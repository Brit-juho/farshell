# Multi-host peering

> `CLAUDE.md`의 영역 색인에서 갈라져 나온 문서다(2026-09-18). 이 영역을 만지기 전에 읽는다.

## Features

| Feature | Description |
|------|------|
| Offline host layout (C3) | A pane whose session belongs to a **remote** host and can't be found on restore is no longer demoted to an empty pane — it keeps its place as `unreachable` and says which host/session it is waiting for, with [다시 시도] (re-checks `GET /api/hosts?fresh=1`) and [다른 세션 고르기]. A briefly powered-off host and a dead session are different things: demoting both means turning the host back on never brings the layout back. Local sessions are still demoted — a tmux name that isn't there locally really is gone. The leaf's `host` is now persisted (`frontend/js/layout/persist.js`), and a re-save keeps the waiting state instead of erasing it |
| Multi-host peering (N7/N39, stage 1) | Two Macs each running FarShell, paired **server-to-server** — not SSH. Decided 2026-09-12 over the original SSH-attach plan because SSH can't do any of: revoke one connection without touching other logins, start read-only, or leave an audit trail. `fsh host pair` (on B) issues a one-time 5-minute ticket; `fsh host add <url> --ticket <t>` (on A) redeems it for a **per-connection secret**. Requests carry `id+ts+nonce+HMAC` and **never the secret itself** (60s window, one-time nonce, signature bound to method+path) — the same trade as an SSH private key: plaintext on 0600 disk, never on the wire. Default grade is `view` (read-only); `fsh host allow-control <id>` is the explicit opt-in to input. Deliberately a **separate `/api/peer/*` namespace** (`server/routes/peer.py`) so a leaked peer secret reaches nothing else — regression-tested. Revoking (`fsh host rm`) makes still-valid signatures 404 immediately. `~/.vt/hosts.json` (0600) keeps the two directions separate (`peers` outbound / `grants` inbound); `local`/`self`/`me` are reserved ids. Audit log at `~/.vt/peer_audit.log` (`fsh host log`), emergency `fsh host revoke-all`. Stage 1 shipped here; remote sessions (stage 2) and input (stage 3) followed in 2.1.2/2.1.3 — see below |

## Multi-host stage 3 — remote panes (N7/N39)

A remote tmux session opens as a normal tab/pane through a **WS proxy**: browser → this server (usual login auth) → the other server's `/api/peer/ws/{name}` (peer signature). A browser WebSocket can't send the signature headers, which is why this is server-to-server at all. Input requires the `control` level (`fsh host allow-control <id>`) and **the owning host decides** — the proxy forwards without judging.

Each proxy connection gets its own PTY on the owner and it dies with the connection (sharing the owner's PTY would make two screens fight over the terminal size).

Three traps closed on purpose: the proxy never feeds the output watcher or writes scrollback (**only the host that owns the PTY notifies and persists**, so nothing doubles); "Connected screens" was hidden for remote sessions **through 2.1.2** (`/api/tmux/clients` reads *this* mac's tmux and derives "me" from a local PTY tty — "keep only this screen" could cut you off). **2.1.3 opened it**: the list and the detaches go to the host that owns the PTY (`/api/peer/clients{,/detach,/solo}`), and "me" is decided there from a screen token the browser minted, pinned inside a `peer-<caller id>-` prefix. **The list is `view`, detaching is `control`**; file insert into a remote pane is refused with a reason (the bytes only exist on this mac).

Client entry point: `frontend/js/term/remote.js` (`window.attachRemoteSession`), which the rail row and the C3 placeholder's [다시 시도] both call

**A2 (2.1.2): a file can now be inserted into a remote pane** — the bytes go first (`POST /api/files/{id}/send` → the peer's `POST /api/peer/file`, `control` level), then that host types **its own** path into the pane. This is the only call whose signature also covers a **body hash** (`X-Peer-Body`): every other peer body is small JSON, a file is a large blob crossing a tunnel, so "signature valid but bytes differ" has to be distinguishable. Re-sends are deduped by origin (sender host + their file id), never by content hash — same content from a different sender is a different file, and hashing 200MB per send buys nothing.

## Remote session management + one "which host am I looking at" (2026-09-28)

**Create, kill and rename a tmux session on the other Mac** — until now a remote host was read-and-type only: the rail's `+ 새 세션` was disabled there and remote rows had no menu. The owner exposes `POST /api/peer/sessions/{create,kill,rename}`, all **`control` level** (control can already type anything into a shell, so starting or ending one grants nothing new; giving it to `view` would let a watch-only peer end your work). The owner never takes a `cwd` or a command — a session starts in its own default directory with the default shell, so "create a session" can't become a second way to run a command. Names are `[A-Za-z0-9_][A-Za-z0-9_-]{0,31}`: no leading `-`, because in `rename-session -t =old NEW` tmux would read it as an option.

**Targets are matched exactly (`-t =name`).** Plain `-t name` falls back to a *prefix* match when there is no exact one — measured 2026-09-28: `has-session -t dev` succeeds when only `dev-2` exists — so a kill of `dev` would have ended `dev-2`. The older local paths (`/api/tmux/kill`, `/api/peer/ws`) still use plain `-t`; that is a known, separate gap.

The browser calls this side's `/api/hosts/{id}/sessions` (POST / DELETE / PATCH), which proxies and drops the 30s session-list cache. A peer that predates these routes answers 404 with no `session_not_found` body, and this side turns that into **501 `peer_outdated`** so the toast says "update that Mac" rather than "not found". Kill closes the open tab **before** asking the owner (same order as the local kill). Rename does **not** reconnect: the owner's attach PTY is a tmux client and follows the rename; only the tab record's `remote.tmux` changes, and `term/ws.js` now rebuilds the proxy path from the record on every connect, so a later reconnect uses the new name. Open remote tabs are found by record (host + tmux), not by the `remote:<host>:<tmux>` id, which keeps the old name after a rename.

**Proxy close codes now reach the browser.** `routes/peer_proxy.py` used to close the browser side with 1000 whatever the owner said, so a tab whose remote session was gone (killed or renamed on the owner) retried forever. The owner's 4404 (no such session) / 4401 (auth refused) are now forwarded as 4004 / 4001, which `term/ws.js` treats as "don't retry".

**Header chip, rail switcher and pane agree** (`frontend/js/term/host-view.js`). The switcher used to be a list filter only and the chip showed the logged-in server, read once at boot — choosing M5 left the chip saying M1 and the pane showing an M1 session. The single rule now: *the host of the active pane* — its session's host, or, for an empty pane, its tab's `hostId` (the slot `layout/store.js` had kept at `'local'` since 2.0). Choosing a host in the switcher moves the screen there (its first open session, else an empty tab for that host, reused if one exists); focusing another pane moves the switcher back; the chip shows the remote host with "· <this Mac> 경유". An empty pane in a remote host's tab draws a "no open screen · + new session on <host>" placeholder instead of the local session picker, which would only ever list this Mac's sessions. The phone fleet screen (`Fleet.tsx`) still treats its host picker as a filter.

**A remote tab learns at once that its session is gone.** The owner's `/api/peer/ws` used to wait only on the browser side, so when the tmux session died the attach PTY exited (`[process exited]`) but the socket stayed open and the tab showed a dead screen until the next reconnect. The output pump now checks after each chunk whether its PTY is still registered; if not, and the tmux session no longer exists (exact match), it closes with 4404 → the proxy forwards 4004 → the browser shows "재연결 중단" immediately. If the session is still alive (only this screen was detached, e.g. "keep only this screen"), the socket is left alone — closing would make the browser reattach and undo the detach.
