# Multi-host peering

## Features

| Feature | Description |
|------|------|
| Offline host layout | A pane whose session belongs to a **remote** host and can't be found on restore is not demoted to an empty pane — it keeps its place as `unreachable` and says which host/session it is waiting for, with [다시 시도] (re-checks `GET /api/hosts?fresh=1`) and [다른 세션 고르기]. A briefly powered-off host and a dead session are different things: demoting both means turning the host back on never brings the layout back. Local sessions are demoted — a tmux name that isn't there locally really is gone. The leaf's `host` is persisted (`frontend/js/layout/persist.js`), and a re-save keeps the waiting state instead of erasing it |
| Multi-host peering | Two Macs each running FarShell, paired **server-to-server** — not SSH, because SSH can't do any of: revoke one connection without touching other logins, start read-only, or leave an audit trail. `fsh host pair` (on host B) issues a one-time 5-minute ticket; `fsh host add <url> --ticket <t>` (on host A) redeems it for a **per-connection secret**. Requests carry `id+ts+nonce+HMAC` and **never the secret itself** (60s window, one-time nonce, signature bound to method+path) — the same trade as an SSH private key: plaintext on 0600 disk, never on the wire. Default grade is `view` (read-only); `fsh host allow-control <id>` is the explicit opt-in to input. Deliberately a **separate `/api/peer/*` namespace** (`server/routes/peer.py`) so a leaked peer secret reaches nothing else — covered by a regression test. Revoking (`fsh host rm`) makes still-valid signatures get 401 `unregistered` at once. `~/.vt/hosts.json` (0600) keeps the two directions separate (`peers` outbound / `grants` inbound); `local`/`self`/`me` are reserved ids. Audit log at `~/.vt/peer_audit.log` (`fsh host log`), emergency `fsh host revoke-all`. Remote sessions and input are described below |

## Remote panes

A remote tmux session opens as a normal tab/pane through a **WS proxy**: browser → this server (usual login auth) → the other server's `/api/peer/ws/{name}` (peer signature). A browser WebSocket can't send the signature headers, which is why this is server-to-server at all. Input requires the `control` level (`fsh host allow-control <id>`) and **the owning host decides** — the proxy forwards without judging.

Each proxy connection gets its own PTY on the owner and it dies with the connection (sharing the owner's PTY would make two screens fight over the terminal size).

Two traps are closed on purpose. The proxy never feeds the output watcher or writes scrollback (**only the host that owns the PTY notifies and persists**, so nothing doubles). "Connected screens" for a remote session cannot use `/api/tmux/clients`, which reads *this* Mac's tmux and derives "me" from a local PTY tty ("keep only this screen" could cut you off); instead the list and the detaches go to the host that owns the PTY (`/api/peer/clients{,/detach,/solo}`), and "me" is decided there from a screen token the browser minted, pinned inside a `peer-<caller id>-` prefix. **The list is `view`, detaching is `control`**; file insert into a remote pane is refused with a reason (the bytes only exist on this mac).

Client entry point: `frontend/js/term/remote.js` (`window.attachRemoteSession`), which the rail row and the offline placeholder's [다시 시도] both call.

**A file can be inserted into a remote pane** — the bytes go first (`POST /api/files/{id}/send` → the peer's `POST /api/peer/file`, `control` level), then that host types **its own** path into the pane. This is the only call whose signature also covers a **body hash** (`X-Peer-Body`): every other peer body is small JSON, a file is a large blob crossing a tunnel, so "signature valid but bytes differ" has to be distinguishable. Re-sends are deduped by origin (sender host + their file id), never by content hash — same content from a different sender is a different file, and hashing 200MB per send buys nothing.

## Remote session management and the active host indicator

**Create, kill and rename a tmux session on the other Mac.** The owner exposes `POST /api/peer/sessions/{create,kill,rename}`, all **`control` level** (control can already type anything into a shell, so starting or ending one grants nothing new; giving it to `view` would let a watch-only peer end your work). The owner never takes a `cwd` or a command — a session starts in its own default directory with the default shell, so "create a session" can't become a second way to run a command. Names are `[A-Za-z0-9_][A-Za-z0-9_-]{0,31}`: no leading `-`, because in `rename-session -t =old NEW` tmux would read it as an option.

**Targets are matched exactly (`-t =name`).** Plain `-t name` falls back to a *prefix* match when there is no exact one (`has-session -t dev` succeeds when only `dev-2` exists), so a kill of `dev` would end `dev-2`. The local paths (`DELETE /api/tmux/kill/{tmux_name}`, `/api/peer/ws`) use plain `-t`; that is a known gap.

The browser calls this side's `/api/hosts/{id}/sessions` (POST / DELETE / PATCH), which proxies and drops the 30s session-list cache. A peer too old to have these routes answers 404 with no `session_not_found` body, and this side turns that into **501 `peer_outdated`** so the toast says "update that Mac" rather than "not found". Kill closes the open tab **before** asking the owner (same order as the local kill). Rename does **not** reconnect: the owner's attach PTY is a tmux client and follows the rename; only the tab record's `remote.tmux` changes, and `term/ws.js` rebuilds the proxy path from the record on every connect, so a later reconnect uses the new name. Open remote tabs are found by record (host + tmux), not by the `remote:<host>:<tmux>` id, which keeps the old name after a rename.

**Session origin crosses the wire.** `GET /api/peer/sessions` items carry `origin` (`local`/`peer`/`external`), read from the owner's own `@fsh_origin` in the same `list-sessions` call — the same values and normalisation (`tmux_runner.normalize_origin`: no record or an unknown value = `external`) as the local `GET /api/tmux/sessions`. It describes how the session was created **on that host**, so a session this side created there (`/api/peer/sessions/create`) comes back as `peer`, and a plain `tmux new` on the other Mac as `external`. The field is outside the request signature (it is response data, nothing new to sign); a peer too old to send it omits the field and the frontend treats the row as local. `/api/hosts/{id}/sessions` passes the list through untouched, and the frontend renders whatever `origin` arrives. The host list's own `local` entry (`hosts._local_entry`) carries `origin` on each session too, read from the same `get_all_panes` result as `command`/`cwd` (no extra tmux call; a session without a pane record reads `external`).

**The proxy watches both hops for zombie connections** (`routes/peer_proxy.py`, same thresholds as a local pane; details in [`reliability.md`](./reliability.md) «WebSockets»). Browser side: the proxy pings every 15 s and closes with 1001 after 45 s of silence; owner side: protocol ping/pong every 15 s with a 15 s deadline, a failure closes upstream with 1011. Either way the browser gets a reconnectable code (1000/1001), so a stalled owner never becomes 「재연결 중단」 and an offline host's layout is kept; its `pong` replies are swallowed by the proxy, not forwarded.

**Proxy close codes reach the browser.** `routes/peer_proxy.py` forwards the owner's close reason instead of closing with 1000, since a tab whose remote session is gone (killed or renamed on the owner) would otherwise retry forever. The owner's 4404 (no such session) / 4401 (auth refused) are forwarded as 4004 / 4001, which `term/ws.js` treats as "don't retry".

**Header chip, rail switcher and pane agree** (`frontend/js/term/host-view.js`). The single rule: *the host of the active pane* — its session's host, or, for an empty pane, its tab's `hostId` (a slot in `layout/store.js`). Choosing a host in the switcher moves the screen there (its first open session, else an empty tab for that host, reused if one exists); focusing another pane moves the switcher back; the chip shows that host. An empty pane in a remote host's tab draws a "<label> · no open screens" placeholder with a "+ New session in <label>" button instead of the local session picker, which would only ever list this Mac's sessions. The phone fleet screen (`Fleet.tsx`) switches the whole app to the chosen host, like the rail.

**A remote tab learns at once that its session is gone.** The owner's `/api/peer/ws` must not wait only on the browser side, or a dead tmux session would leave the socket open and the tab on a dead screen (`[process exited]`) until the next reconnect. The output pump checks after each chunk whether its PTY is still registered; if not, and the tmux session no longer exists (exact match), it closes with 4404 → the proxy forwards 4004 → the browser shows "재연결 중단" immediately. If the session is still alive (only this screen was detached, e.g. "keep only this screen"), the socket is left alone — closing would make the browser reattach and undo the detach.

## Host switch — the whole app follows the chosen Mac

**The rail/phone host switcher is not a list filter or a "jump to that host's pane".** Choosing host-b makes the *entire* app host-b: sessions, top tabs, ports, files, attachments, queue, snippets, git, usage, settings. The browser stays logged in to host-a only (cookie, OTP, device registration all live there); host-a relays every host-scoped call to host-b.

- **Client** (`frontend/js/core/host-route.js`): the choice lives in `localStorage` (`vt.relayHost`) and is read **once at boot**. Switching = save + reload the same URL (a reload can't leave half the app on one host and half on another through late responses). `vtFetch`/`apiFetch`/`vtUrl`, the upload XHR and the five WebSocket routes rewrite `/api/x` → `/api/hosts/<id>/relay/api/x` and `/ws/...` → `/ws/hosts/<id>/relay/ws/...`. What stays local is what belongs to *this browser/login*: `/api/agent-profiles`, `/api/agent-config`, auth, devices, device settings, `/api/hosts`, `/api/peer`, push, notify, clipboard, voice. `hostKey()` suffixes `@<host>` onto the localStorage keys for the layout, the settings cache, recent files and the onboarding session cache; the E2E identity pin appends `@<host>` itself (`frontend/js/term/e2e.js`). The workspace is not stored per host in localStorage: `/api/workspace` and `/ws-workspace` are relayed to the chosen host. At boot, if the chosen host was removed / downgraded / is outdated, the app returns to this Mac with a toast; an **offline** host is kept (it's the user's choice and should resume when it comes back).
- **Sending side (host-a)** (`server/routes/host_relay.py`): signs and forwards; strips `token` from the query; never forwards cookies/Authorization nor returns `Set-Cookie`; no redirects followed. A response without `x-peer-relay: 1` means the peer is too old to relay → 501 `peer_outdated`.
- **Receiving side (host-b)** (`server/routes/peer_relay.py`): signature covers **path + query** (the query picks the target — `/api/fs/raw?path=`) and a **mandatory** body hash; **`control` only**; then runs its own router in-process with a `vt_relay` scope key (only server code can set scope keys — `_ws_auth_token` honours it). Relayed WebSockets re-check the grant periodically (every 30 s, or every 2 s with `VT_AUTHZ_ENFORCE=peer`).
- **Allowlist, not denylist** (`server/relay_policy.py`): a new API is unreachable from a peer until listed. Never relayed: auth/devices/OTP/elevation, host & peer management (would allow A→B→C chaining), share links, port expose, git accounts, MCP writes, push, clipboard, voice, hook events. Elevated routes also fail inside because there is no cookie — a second lock.
- **Response headers are host-a's, not host-b's** (`relay_policy.response_headers`, used by `host_relay.py`). host-b's bytes open in **host-a's origin**, so a malicious or compromised host-b must not be able to weaken host-a's policy. host-a rebuilds the headers instead of copying them:
  - `X-Content-Type-Options: nosniff` — always host-a's (host-b's value is discarded; it could send `x` and turn sniffing back on).
  - `Content-Security-Policy` — host-b's is **dropped** and host-a sets `default-src 'none'; frame-ancestors 'none'; sandbox` (`relay_policy.RELAY_CSP`). Dropping beats appending: an appended policy would still carry host-b's `report-uri`/`report-to` (CSP reports from host-a's origin sent to host-b's URL). Nothing relayed is a document — JSON is read by `fetch`, images by `<img>`, downloads are attachments, and none of those read a response's CSP — so the strict policy breaks nothing, and it is stricter than any policy a relayed route sets today. `X-Frame-Options: DENY` comes from host-a's `SecurityHeadersMiddleware` as usual.
  - `Content-Type` — an allowlist per route: `application/json` everywhere; on `/api/fs/raw` the `fsguard.raw_types()` — images, SVG, video, audio (host-b already checks extension and magic bytes; host-a forces `Content-Disposition: inline`, and its sandbox CSP keeps a relayed SVG from running script even when opened directly); on `/api/files/{id}/download` any type, with `Content-Disposition: attachment` forced and active types (HTML, SVG, XML, JS, …) turned into `application/octet-stream`. Anything else — `text/html`, `image/svg+xml`, XML, JavaScript, a missing type with a body — is **neutralised** to `text/plain; charset=utf-8` with the same status (and logged) rather than refused, so an unexpected error body from host-b still reaches the caller as an inert error. Before 2026-11 the type passed through, so host-b answering `text/html` ran script in host-a's origin.
  - Everything else is an allowlist too: only `content-length`, `etag`, `last-modified`, `content-range`, `accept-ranges` are copied. `Set-Cookie`, `Location`, `Refresh`, `Link`, `Access-Control-*`, `Clear-Site-Data`, `Service-Worker-Allowed`, `Strict-Transport-Security`, `X-Frame-Options` and any other header from host-b never reach the browser. `Cache-Control` becomes `no-store` (when host-b said `no-store`) or `private, no-cache`, so a shared cache in front of host-a never stores host-b's answers.
  - host-b (`peer_relay.py`, `_PASS_RESPONSE_HEADERS`) sends only content headers to host-a; it no longer forwards its CSP/`nosniff`, since host-a would ignore them.
- **Request headers that cross the relay** (`_PASS_REQUEST_HEADERS` in `peer_relay.py`, shared by `host_relay.py`): content type, `accept`, conditional headers, and `range` with `if-range` together (a `range` without its validator could stitch a changed file onto the old part). Cookies never cross in either direction.
- **Files on a remote host**: file *reading* features are relayed (viewer, tree, raw images, filename search, content search `/api/fs/grep` — host-b searches its own roots with its own deny rules, and the result paths are host-b paths that the browser opens through the same relay; new read routes are added to the allowlist as `GET`). Path-based file *writing* and path-based *download* stay local-only and are not in the allowlist: the relay carries no cookie, so host-b's elevation cannot be passed, and remote writes would need their own elevation design. The rule is recorded at the top of `relay_policy.py`.
- The header chip shows **only the chosen host** (there is no "via this Mac" suffix).
- Known limits: voice input and push notifications stay tied to the Mac you logged in to; opening a port preview uses that Mac's tunnel URLs as reported by it.

## Access is decided by grants, not by the signature (`VT_AUTHZ_ENFORCE=peer`)

The signature only says which Mac is calling. With `VT_AUTHZ_ENFORCE=peer` what that Mac may do comes from its grant (`view` or `control`, plus
the agent-message switch), checked per route and again for every typed frame on an open terminal; a Mac you remove or downgrade is
disconnected within 5 seconds. **`control` is a remote shell**: that Mac can type into every terminal here, create and kill sessions, send
files and use the relayed API — treat it like an SSH login. On the sending side only a person logged in through the browser can use the
host list, remote session actions and the host switch; an agent or the machine token cannot. Raising a Mac's access with `fsh host allow-*`
becomes an approval request that a person confirms in the web inbox. Details: [`auth.md`](./auth.md).

## Another Mac's agents, protocol v2 (`VT_AUTHZ_ENFORCE=peer`)

An agent on one Mac can read and type into a session **shared** on another Mac and can have that Mac create a sub-session, without becoming a `control` shell. The calling
Mac vouches for its agent (`X-Peer-Obo`, signed); the receiving Mac's person approves in the normal web inbox, and the share policy there is the ceiling. MCP tools
`read_session`, `send_to_session`, `list_shared_sessions`, `spawn_session` and `list_delegations` take a `host` argument (a host id from `fsh host list`) only when the server
has the flag on; the answer to a first use is «waiting for approval, call again». Instructions to the child, results back to the parent's queue and closing follow the delegation
ledger, which records the other Mac as `host`. Revoking on the receiving Mac cuts open terminal streams on the other side within 5 seconds, and a signed revoke notice (re-checked
by asking the sender) cleans the rest. `fsh host rotate <id>` rotates a connection's secret on both sides atomically (the previous secret survives any failure). Protocol, limits and
what is not built: [`auth.md`](./auth.md) «Other Macs, grant based»; endpoints: `API.md`.
