# Tunnels, ports, remote access

## Features

### Port dashboard

Dock tab "Ports (포트)" (`shell/Dock.tsx`). Handles "what's running right now / kill port 3000" from the phone when you're away from the Mac. Shows port·PID·uptime·CPU·memory, one-click kill, integrates with `fsh tunnel expose`. **Killing the VT server itself, or cloudflared/tailscaled/sshd, is blocked** — killing them would cut off this very screen. Other users' processes are also blocked (no sudo used). Right before killing, `port→pid` is re-checked to prevent PID reuse from killing the wrong process, returning 409 on a mismatch. `expose` makes the local server reachable from the **public internet** (even in `session`/`pin` mode — the tunnel itself is public, only the app-layer gate is private), so it returns 428 without `confirm:true` and is refused outright unless `VT_NETWORK_MODE` is `all` (there's no point narrowing access scope and then reopening it) — all three modes are blocked, not just `public`. `expose`/its PIN reissue/mode change require an **elevated** session (same tier as issuing a file share link). Checked in `server/portscan.py`/`server/routes/ports.py`

### Tunnel provider (`VT_TUNNEL_PROVIDER`)

Who owns the public way in: `cloudflare` (default) · `ngrok` · `none`. `start`/`stop`/`status`/`mobile`/`handoff`/`tunnel expose` all follow it, and `_main_tunnel_url` in `bin/fsh` is the single place that knows which URL is current (status, QR and the hook all use it). **ngrok** takes `VT_NGROK_DOMAIN` for a reserved address (without it every start gets a throwaway URL); extra ports still work but get throwaway URLs, since the reserved domain is used by the main tunnel. The **watchdog stays cloudflare-only** — the detector reads cloudflared's log format. The **URL-change hook only fires when the address actually changed** under ngrok, so a reserved domain does not republish the same URL on every start. `server/tunnel.py`'s `get_tunnel_status()` is provider-aware for the same reason the CLI is: it feeds the `tunnel` field embedded in `/api/capabilities` and the ports panel, which would otherwise say "tunnel down" while ngrok is serving fine. `ngrok` is also in `portscan.py`'s protected list — killing it from the phone's port dashboard would cut the very screen issuing the kill

### Extra port tunnels

`fsh tunnel expose <port>` — one tunnel is spun up per port, tracked by fsh via PID/registry

### Exposed-port access control

Three modes for who can open an exposed port — `public` (URL only), `session` (default — logged-in FarShell devices only), `pin` (server-generated code, valid for the life of the exposure). **Every mode is routed through FarShell's own reverse proxy**, not straight to the app — `cloudflared --url` points at a per-share loopback listener (`server/port_proxy.py`), never at the app port itself. There is deliberately no path-prefix design (`/p/<slug>/…` on the main tunnel): it would put the exposed app in the **same origin** as the terminal, letting its JS call `/api/tmux/*` with the browser's session cookie — the same reasoning that keeps the code viewer from rendering HTML/SVG inline. Each proxy listener runs on its own port with exactly three routes (`/__fsh/cb`, `/__fsh/pin`, catch-all) — FarShell's own API routes are **not mounted there**, so the isolation is structural rather than resting on middleware ordering. Policy lives in `~/.vt/port_shares.json` (0600) — PINs are scrypt-hashed, never stored in plaintext; a share's `proxyPort` is allocated once and kept stable across `fsh restart` since `fsh stop --keep-tunnel` leaves the cloudflared process (and therefore the URL) alive and it needs to find the same local address again. `session` mode needs a handshake because the exposed host and the main tunnel are different origins — `vt_session` won't travel there — so `GET /p/authorize` (on the main origin) checks login+device and hands the exposed host a 60-second one-time ticket instead. `fsh tunnel expose/pin/mode` write the policy directly via `python -m port_share_store` (same trust tier as `fsh git-account`/`fsh otp setup` — local shell access, not the web session's elevation gate) and then hit the non-elevated `POST /api/ports/_proxy/sync` to make the running server pick it up immediately.

### Exposed-port hardening

The proxy gate is not enough on its own: what the proxy passes on matters too. Current behavior: (1) Client-supplied `X-Forwarded-*`, `Forwarded`, `X-Real-IP`, `True-Client-IP` and `cf-*` headers are stripped and replaced by one value each (`_upstream_headers`), so an app reading the first value cannot be fooled by `X-Forwarded-For: 127.0.0.1` from the internet. The Host rewrite to `localhost:<port>` is kept for Vite, which is exactly why an app's own "localhost only" checks mean nothing behind this proxy. (2) A PIN reissue or mode change rotates `shareId` (it is not part of the URL; `proxyPort` is what keeps the URL alive), so cookies from the old PIN stop working. (3) The port cookie is validated with `auth.find_alive_device` like the session check, and is capped by the device's remaining life. (4) WebSockets are re-checked every 60s by `_ws_handler` (`_ws_still_admitted`: same mode + share id, cookie still valid) and closed with 4001. (5) A cookie-less visitor to a `session` share sees a notice, not a redirect to the main origin's `/p/authorize`, so the terminal's address is not revealed to anyone holding the app link; the entry point lives on the FarShell side (ports panel, `fsh tunnel expose` output), and the panel asks a relayed host for **its** main URL. (6) Remote-control ports (Chrome DevTools 9222, Node inspector 9229, Docker API 2375/2376, ngrok agent API 4040–4043, cloudflared metrics 20241–20245, our own proxy range) need an explicit second confirmation — `--force` / `force_danger: true` — judged by one function, `port_share_store.danger_reason`. The web client keeps no copy of the list: the first `POST /api/ports/{port}/expose` goes out without `force_danger`, and only a 409 `dangerous_port` opens `panels/ports/danger-confirm.js`, which shows the server's reason and enables Expose (공개) only when the typed text equals the port number (surrounding whitespace ignored, so paste works; `09222` does not match; focus starts on Cancel (취소), Esc/backdrop cancel). Only then is the request resent with `force_danger: true`; the server still refuses anything but the boolean `true` (`test_port_proxy_hardening.py`). (7) PIN: per-IP lockout is 5 failures / 60s and never locks the share (a scanner must not be able to kill a demo); failures are counted (`attempts`, shown in `fsh tunnel list`) and logged with the IP; scrypt runs at most 2 at a time server-wide; the lockout key uses the **rightmost** `X-Forwarded-For` hop (the leftmost is client-controlled and would let one client rotate its way past the lockout); the form body is capped at 4KB; `next` survives via a hidden field; PIN and notice pages send `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `no-store`, `no-referrer`. (8) `routes/ports.expiry_sweep_loop` tears down tunnel, listener and policy of an expired share within a minute, skipping a port that was re-exposed in between. **Auto re-expose** (`autoRenew` + `ttl` on the policy, opt-in per exposure — `--auto-renew`, a y/N prompt on a TTY, or the web dialog's checkbox): the sweep extends such a share by its `ttl` instead of tearing it down, keeping share id and PIN, and `restore_auto_renew_tunnels` (same loop, right after) re-runs `fsh tunnel expose --proxy-port` for every auto share whose tunnel isn't alive in the registry — that's what brings it back after a reboot or full `fsh stop`, since `port_proxy.sync()` restores listeners but never cloudflared. It respects `VT_NETWORK_MODE` like `expose`, and a quick tunnel returns with a new URL (fires the `expose` hook event). Extra-port tunnels have no zombie watchdog; only a dead process is noticed. `server/tests/conftest.py` unsets `VT_DIR` so no test can reach the real `bin/fsh` through `_run_vt`

### URL survival across restarts (`fsh restart`)

An anonymous quick tunnel's address follows the **cloudflared process**, which `fsh stop --keep-tunnel` leaves running, so restarting the server must not stop the tunnel, otherwise **every restart burns the URL**, taking bookmarks, open tabs and the phone's home-screen icon with it. `frontend/sw.js` falls back to the cached shell when the network fetch fails, so a lost URL is not visible from the page alone. `_start_tunnel` reuses a running cloudflared, so only the stop side matters: `fsh stop --keep-tunnel` leaves the entrance (and the watchdog, and `expose`d port tunnels, which front *other* apps) alive, and `fsh restart` is that plus `cmd_start`. The stop hook is **not** fired for `--keep-tunnel` — the entrance is still up, so "stopped" would be a lie. The `start` hook is gated on the last published URL for every provider, because a reused tunnel republishes an unchanged address and the contract is "called when the URL changes". The gate is on `start` alone: `expose`/`unexpose` change the list while the main URL stays put, `manual` is a direct user request, and `stop` carries an empty URL as its payload. The orphan cleanup at the end of `cmd_stop` must kill listeners only — `lsof -iTCP:$VT_PORT -sTCP:LISTEN -t`. Plain `lsof -i :$VT_PORT` also returns cloudflared's own connection to `localhost:$VT_PORT` (present whenever someone is connected) and would burn the URL, and it would kill browsers/peers connected to the port

### Tunnel URL change hook

`VT_TUNNEL_HOOK` — runs an arbitrary command when the URL changes (stdin: `label<TAB>URL`). Since publishing targets differ per person (Notion/Slack/ntfy/file), fsh doesn't know about the service itself. Examples and caveats: `fsh help tunnel-hook`

### Automatic tunnel zombie-reconnect recovery

A cloudflared process can stay alive while it keeps failing to reconnect. `server/tunnel_watchdog.py` auto-starts with `fsh start`/`voice`/`mobile`, watches `$VT_RUN_DIR/cloudflared.log` for reconnect-failure patterns (default: 4+ times within 90 seconds, `VT_TUNNEL_WATCHDOG_THRESHOLD` / `VT_TUNNEL_WATCHDOG_WINDOW_SEC`), and automatically calls `fsh tunnel restart`. Manual check/start: `fsh tunnel watchdog`; manual forced restart: `fsh tunnel restart`

### Tailscale remote access

`fsh ssh` — connect directly to tmux via SSH on networks where screen remoting is blocked (e.g. corporate networks). `fsh mobile --network tailscale` also restricts the web UI to the tailnet only

### Client connection notifications

`VT_NOTIFY_CLIENT_EVENTS=1` — tmux client-attached/detached hook → ntfy/Telegram push

### Email gate in front of the quick tunnel (`VT_TUNNEL_ALLOWED_MAIL`)

Opt-in. With `VT_TUNNEL_ALLOWED_MAIL` (emails or `*@domain`, comma-separated) the main quick tunnel starts as `cloudflared tunnel --allowed-mail <list> --url http://localhost:$VT_PORT`. The flag goes **before** `--url` because every pgrep pattern for the main tunnel is anchored on the command line ending in `--url http://localhost:$VT_PORT`. Values outside `[A-Za-z0-9._%+@*,-]` refuse to open the tunnel rather than open it without the gate. Named tunnels and ngrok are unaffected. It is a boundary key (`server/vt_env.py`). Change → `fsh tunnel restart`. Verified with a fake `cloudflared` on `PATH` (argument order, refusal, unset = no flag).

### Runtime folder (`VT_RUN_DIR`)

Logs, pid files and the extra-port registry (`vt-pids/tunnels.tsv`) live in `VT_RUN_DIR`, by default `${VT_STATE_DIR:-~/.vt}/run` — the folder of the unix socket. The default is deliberately not the shared `/tmp` with fixed names: with `mkdir -p` / `: >` reusing whatever is already there, another account on the same Mac could pre-create `/tmp/vt-pids` or `/tmp/cloudflared.log`, write its own trycloudflare URL into the log (the URL regex accepts any trycloudflare host) and have `fsh mobile`'s QR ticket and `/p/authorize`'s port ticket sent there, or plant pid files for `fsh stop` to kill. Extra-port cloudflared logs (`cloudflared-<port>.log`) honour `VT_RUN_DIR` as well. `lib/run_dir.sh` `_vt_private_dir` (bin/fsh) and `vt_paths.check_private_dir` (server start-up) use the folder only if it is mine, not a symlink and 0700 (a loose folder of mine is tightened; anything else refuses to start). Migration from an older `/tmp` layout: `cmd_stop` (so `stop`, `restart` and `update --restart`) and `cmd_start` (only when the server is not running) move my own, non-symlink files from `/tmp` once (`_vt_migrate_legacy_run`), only for a default install (neither `VT_RUN_DIR` nor `VT_STATE_DIR` set — an isolated instance must not take the default instance's pid files) and not when the new folder is already in use; an old tunnel watchdog (its environment still says `VT_RUN_DIR=/tmp`, so it would watch a log that is no longer there) is ended when its command line really is the watchdog, and the `start` that follows brings up a new one. **Nothing else migrates** — a server started before the upgrade keeps reading `/tmp` until it is restarted, so `fsh update trust`, `fsh tunnel …`, `fsh mobile` and friends must not move its files from under it (the server, tunnel and watchdog would lose their pid files and tunnel log). `fsh status` warns while such a server still runs from `/tmp`. Older `bin/fsh` always exported `VT_RUN_DIR=/tmp`, so tmux panes, daemons and the watchdog started back then still carry it; both `bin/fsh` and `vt_paths.run_dir()` treat `/tmp`·`/private/tmp` as unset (a folder *under* `/tmp` is still honoured), otherwise `fsh restart` typed in such a pane would be refused and nothing would be moved. Tests: `server/tests/test_runtime_dir.py` (sources only `lib/run_dir.sh` — running all of `bin/fsh stop` would also hit this tree's live daemons).

### Reading the quick-tunnel URL

One entry point, `_quick_tunnel_url_from_log` in `bin/fsh`: `grep -a` and the **last** URL. The log can contain NUL bytes (another cloudflared may truncate `cloudflared.log` while the original keeps writing at its old offset); without `-a`, BSD grep prints "Binary file … matches", which fsh would take for the URL. The log alone can't prove a URL is live, so `_run_tunnel_hook` checks it first (`_tunnel_url_alive`: 000/530/1033 = dead, 502 = alive with the server down, 20 tries × 3s for DNS, `VT_TUNNEL_ALIVE_TRIES`) and skips publishing a dead one. A fresh quick tunnel can take longer than those 60s, so on `start` the skip hands off to a background retry (`fsh tunnel __hook-retry <url>`, pid `tunnel-hook-retry`, log `vt-tunnel-hook-retry.log`): it re-checks every `VT_TUNNEL_RETRY_INTERVAL` (15s) up to `VT_TUNNEL_RETRY_TRIES` (40, ≈10 min), publishes once when the URL answers, gives up if the log's URL changes (a newer start owns that one), and is killed by `fsh stop` and by the next spawn. Only one runs at a time.
