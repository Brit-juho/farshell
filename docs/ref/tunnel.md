# Tunnels, ports, remote access

## Features

### Port dashboard (P3)

⋯ menu → "Ports". Handles "what's running right now / kill port 3000" from the phone when you're away from the Mac. Shows port·PID·uptime·CPU·memory, one-click kill, integrates with `fsh tunnel expose`. **Killing the VT server itself, or cloudflared/tailscaled/sshd, is blocked** — killing them would cut off this very screen. Other users' processes are also blocked (no sudo used). Right before killing, `port→pid` is re-checked to prevent PID reuse from killing the wrong process, returning 409 on a mismatch. `expose` makes the local server reachable from the **public internet** (even in `session`/`pin` mode — the tunnel itself is public, only the app-layer gate is private), so it returns 428 without `confirm:true` and is refused outright unless `VT_NETWORK_MODE` is `all` (there's no point narrowing access scope and then reopening it) — all three modes are blocked, not just `public`. `expose`/its PIN reissue/mode change require an **elevated** session (same tier as issuing a file share link). Checked in `server/portscan.py`/`server/routes/ports.py`

### Tunnel provider (`VT_TUNNEL_PROVIDER`)

Who owns the public way in: `cloudflare` (default) · `ngrok` · `none`. Unset behaves exactly as before. `start`/`stop`/`status`/`mobile`/`handoff`/`tunnel expose` all follow it, and `_main_tunnel_url` in `bin/fsh` is the single place that knows which URL is current — before this, status, QR and the hook each grepped the cloudflared log, so a second provider meant three places to drift. **ngrok** takes `VT_NGROK_DOMAIN` for a reserved address (without it every start gets a throwaway URL, which defeats the point); extra ports still work but get throwaway URLs, since a free account reserves one domain and the main tunnel uses it. The **watchdog stays cloudflare-only** — zombie reconnects are a cloudflared symptom and the detector reads its log format. The **URL-change hook only fires when the address actually changed** under ngrok, because a reserved domain would otherwise republish the same URL on every start. `server/tunnel.py`'s `get_tunnel_status()` is provider-aware for the same reason the CLI is: it feeds the `tunnel` field embedded in `/api/capabilities` and the ports panel, which would otherwise say "tunnel down" while ngrok is serving fine. `ngrok` is also in `portscan.py`'s protected list — killing it from the phone's port dashboard would cut the very screen issuing the kill

### Extra port tunnels

`fsh tunnel expose <port>` — a Cloudflare quick tunnel is a 1:1 host↔port mapping, so a port can't be switched via a path (`/localhost:3000`). One tunnel is spun up per port, tracked by fsh via PID/registry

### Exposed-port access control (2.2, ADR-30~32)

Three modes for who can open an exposed port — `public` (URL only), `session` (default — logged-in FarShell devices only), `pin` (server-generated code, valid for the life of the exposure). **Every mode is routed through FarShell's own reverse proxy now**, not straight to the app — `cloudflared --url` points at a per-share loopback listener (`server/port_proxy.py`), never at the app port itself. That's a deliberate trade: a path-prefix design (`/p/<slug>/…` on the main tunnel) was rejected because it would put the exposed app in the **same origin** as the terminal, letting its JS call `/api/tmux/*` with the browser's session cookie — the same reasoning that keeps the code viewer from rendering HTML/SVG inline. Each proxy listener runs on its own port with exactly three routes (`/__fsh/cb`, `/__fsh/pin`, catch-all) — FarShell's own API routes are **not mounted there**, so the isolation is structural rather than resting on middleware ordering. Policy lives in `~/.vt/port_shares.json` (0600) — PINs are scrypt-hashed, never stored in plaintext; a share's `proxyPort` is allocated once and kept stable across `fsh restart` since `fsh stop --keep-tunnel` leaves the cloudflared process (and therefore the URL) alive and it needs to find the same local address again. `session` mode needs a handshake because the exposed host and the main tunnel are different origins — `vt_session` won't travel there — so `GET /p/authorize` (on the main origin) checks login+device and hands the exposed host a 60-second one-time ticket instead. `fsh tunnel expose/pin/mode` write the policy directly via `python -m port_share_store` (same trust tier as `fsh git-account`/`fsh otp setup` — local shell access, not the web session's elevation gate) and then hit the non-elevated `POST /api/ports/_proxy/sync` to make the running server pick it up immediately.

### Exposed-port hardening (2026-10)

A security review of the proxy found that **the gate held but what the proxy passed on did not.** (1) Client-supplied `X-Forwarded-*`, `Forwarded`, `X-Real-IP`, `True-Client-IP` and `cf-*` headers were forwarded upstream with ours appended, so an app reading the first value took `X-Forwarded-For: 127.0.0.1` from the internet for a local request — they are now stripped and replaced by one value each (`_upstream_headers`). The Host rewrite to `localhost:<port>` stays for Vite, which is exactly why an app's own "localhost only" checks mean nothing behind this proxy. (2) A PIN reissue or mode change kept the share id, so cookies from the old PIN lived up to 12h — both now rotate `shareId` (it is not part of the URL; `proxyPort` is what keeps the URL alive). (3) The port cookie checked only that its device existed — it now uses `auth.find_alive_device` like the session check, and is capped by the device's remaining life. (4) WebSockets were checked once at the handshake; `_ws_handler` now re-checks every 60s (`_ws_still_admitted`: same mode + share id, cookie still valid) and closes with 4001. (5) A cookie-less visitor to a `session` share was redirected to the main origin's `/p/authorize`, revealing the terminal's address to anyone holding the app link — the proxy now shows a notice instead, and the entry point moved to the FarShell side (ports panel, `fsh tunnel expose` output); the panel asks a relayed host for **its** main URL. (6) Remote-control ports (Chrome DevTools 9222, Node inspector 9229, Docker API 2375/2376, ngrok agent API 4040–4043, cloudflared metrics 20241–20245, our own proxy range) need an explicit second confirmation — `--force` / `force_danger: true` — judged by one function, `port_share_store.danger_reason`. Chrome refuses DevTools requests whose Host isn't local; our Host rewrite switches that defence off. (7) PIN: per-IP lockout stays 5 failures / 60s and never locks the share (a scanner must not be able to kill a demo); failures are now counted (`attempts`, shown in `fsh tunnel list`) and logged with the IP; scrypt runs at most 2 at a time server-wide; the lockout key uses the **rightmost** `X-Forwarded-For` hop (the leftmost is client-controlled and let one client rotate its way past the lockout); the form body is capped at 4KB; `next` survives via a hidden field; PIN and notice pages send `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `no-store`, `no-referrer`. (8) Expired shares used to leave cloudflared and the listener up (serving 404) — `routes/ports.expiry_sweep_loop` now tears down tunnel, listener and policy within a minute, skipping a port that was re-exposed in between. **Auto re-expose** (`autoRenew` + `ttl` on the policy, opt-in per exposure — `--auto-renew`, a y/N prompt on a TTY, or the web dialog's checkbox): the sweep extends such a share by its `ttl` instead of tearing it down, keeping share id and PIN, and `restore_auto_renew_tunnels` (same loop, right after) re-runs `fsh tunnel expose --proxy-port` for every auto share whose tunnel isn't alive in the registry — that's what brings it back after a reboot or full `fsh stop`, since `port_proxy.sync()` restores listeners but never cloudflared. It respects `VT_NETWORK_MODE` like `expose`, and a quick tunnel returns with a new URL (fires the `expose` hook event). Extra-port tunnels still have no zombie watchdog; only a dead process is noticed. `server/tests/conftest.py` unsets `VT_DIR` so no test can reach the real `bin/fsh` through `_run_vt`

### URL survival across restarts (`fsh restart`)

An anonymous quick tunnel's address is bound to the **cloudflared process lifetime**, not to the server. Measured 2026-09-21: killing the backend while leaving cloudflared up returns 502 for the gap and then recovers to 200 on the **same URL**. Before this, the only way to pick up code changes was `fsh stop && fsh start`, and that `stop` killed the tunnel too — so **every restart burned the URL**, taking bookmarks, open tabs and the phone's home-screen icon with it. Worse, `frontend/sw.js` serves the cached shell when `fetch` rejects, so a dead origin still *renders* the full UI and the server log shows nothing at all — the failure was invisible from both ends. `_start_tunnel` already reused a running cloudflared, so the fix was only on the stop side: `fsh stop --keep-tunnel` leaves the entrance (and the watchdog, and `expose`d port tunnels, which front *other* apps) alive, and `fsh restart` is that plus `cmd_start`. The stop hook is **not** fired for `--keep-tunnel` — the entrance is still up, so "stopped" would be a lie. The `start` hook is gated on the last published URL for every provider now (it used to be ngrok-only), because a reused tunnel republishes an unchanged address and the contract is "called when the URL changes". The gate is on `start` alone: `expose`/`unexpose` change the list while the main URL stays put, `manual` is a direct user request, and `stop` carries an empty URL as its payload. **2026-09-28 — it still burned the URL whenever someone was connected**: the orphan cleanup at the end of `cmd_stop` ran `lsof -i :$VT_PORT -t | xargs kill`, and `lsof -i` returns every process with a socket *on* that port, including cloudflared's own connection to `localhost:$VT_PORT`. The 2026-09-21 measurement had no live client, so cloudflared held no connection then. Now it is `lsof -iTCP:$VT_PORT -sTCP:LISTEN -t` — listeners only (also stops it killing browsers/peers connected to the port). Reproduced with a fake cloudflared that holds a connection to the port: before, a new URL on every restart; after, the same URL twice in a row

### Tunnel URL change hook

`VT_TUNNEL_HOOK` — runs an arbitrary command when the URL changes (stdin: `label<TAB>URL`). Since publishing targets differ per person (Notion/Slack/ntfy/file), fsh doesn't know about the service itself. Examples and caveats: `fsh help tunnel-hook`

### Automatic tunnel zombie-reconnect recovery

cloudflared can fall into a zombie state where the process is alive (`kill -0` succeeds) but only the QUIC control stream to the edge is cut, endlessly retrying reconnection (static files occasionally return 200, API returns 503). `server/tunnel_watchdog.py` auto-starts with `fsh start`/`voice`/`mobile`, watches `/tmp/cloudflared.log` for reconnect-failure patterns (default: 4+ times within 90 seconds), and automatically calls `fsh tunnel restart`. Manual check/start: `fsh tunnel watchdog`; manual forced restart: `fsh tunnel restart`

### Tailscale remote access (D9)

`fsh ssh` — connect directly to tmux via SSH on networks where screen remoting is blocked (e.g. corporate networks). `fsh mobile --network tailscale` also restricts the web UI to the tailnet only

### Client connection notifications (D9)

`VT_NOTIFY_CLIENT_EVENTS=1` — tmux client-attached/detached hook → ntfy/Telegram push

### Reading the quick-tunnel URL (2026-09-30)

One entry point, `_quick_tunnel_url_from_log` in `bin/fsh`: `grep -a` and the **last** URL. Another cloudflared once truncated `/tmp/cloudflared.log` while the original kept writing at its old offset, leaving NUL bytes; BSD grep then printed "Binary file … matches", which fsh took for the URL (restart stalled, the hook tried to publish it). The log alone can't prove a URL is live, so `_run_tunnel_hook` checks it first (`_tunnel_url_alive`: 000/530/1033 = dead, 502 = alive with the server down, 20 tries × 3s for DNS, `VT_TUNNEL_ALIVE_TRIES`) and skips publishing a dead one. **2026-10-14** — a fresh quick tunnel took longer than those 60s, and since nothing retried, the new URL was never published. On `start` the skip now hands off to a background retry (`fsh tunnel __hook-retry <url>`, pid `tunnel-hook-retry`, log `vt-tunnel-hook-retry.log`): it re-checks every `VT_TUNNEL_RETRY_INTERVAL` (15s) up to `VT_TUNNEL_RETRY_TRIES` (40, ≈10 min), publishes once when the URL answers, gives up if the log's URL changes (a newer start owns that one), and is killed by `fsh stop` and by the next spawn. Only one runs at a time.
