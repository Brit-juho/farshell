# Files, sharing, code viewer

## Features

### File viewer surface

`viewer.surface` setting (Settings → 모양): `sheet` (default) / `float` / `pane`. `sheet`/`float` are overlays mounted inside `#terminal-container` (`panels/viewer/overlay.js`) — opening/closing a file does not resize the pane tree, so xterm never `fit()`s and no `SIGWINCH` reaches vim/tmux/less (a pane-leaf viewer would resize the tree). The overlay's click-through background lets you keep typing in the terminal with the file open; Esc only closes it when focus is inside the card (terminal-focused Esc still reaches vim). `sheet` drags its height (`viewer.sheet.height`, 20–85%) with the shared `wireRatioResizer`; `float` drags position/size (`viewer.float.rect`, a JSON rect, clamped so it can never end up off-screen with no way back). A header button ("페인으로") switches to the `pane` surface for side-by-side reading. `openFileInPane()` opens a pane leaf (used by the overlay header's "페인으로 열기" button); `openFile()` is the default entry point everything else calls, and branches on the setting. Compact (<720px) ignores the setting and always opens a fullscreen sheet with back-button close. All three surfaces share the same renderer (`viewer/file.js:renderFile`) — content code is one copy regardless of surface

### Auto-refresh (`/ws-fs-watch`)

The open file (every surface), the 파일 tab's expanded directories and the 소스컨트롤 tab's change list redraw when the disk changes. `shell/fs-watch.js` subscribes (it lives in the `shell` chunk so the viewer and the rail's git badges share one connection — `core.js` has no room under its initial-payload cap (350KiB for app.js + core.js), and `shell` is loaded at boot anyway; `file` / `dir` / `repo`, full list on every change, connection only while something is subscribed, re-reads everything once after a reconnect); `server/fs_watch.py` answers with "this subscription changed" only — the redraw goes back through `/api/fs/*`·`/api/git/*`, so the browse boundary is unchanged. Subscriptions go through `fsguard.resolve_under_roots`, deny-listed names never trigger. `file` watches the **parent** directory (editors save by rename, which breaks an inode watch). `repo` is widened to the work-tree top and refused outside a git repo (otherwise a session sitting in `~/GitHub` would watch all of it); inside `.git` only `index`/`HEAD`/`refs/` count, so `git status` touching `index.lock`/`objects` cannot trigger itself. All connections share **one flat and one recursive** `watchfiles` watcher — each `awatch` holds a thread from anyio's default pool (40, shared with Starlette's sync routes), so a watcher per connection would eat it. Redraws keep scroll, expansion, the selected row and a half-typed commit message; the source-control tab only redraws while its list is showing, never over an open diff. The rail/fleet git badge also uses `repo` subscriptions: while a cwd's watch is live the count is re-read only after a change (at most every 30s, and once every 10 min as a safety net); if the watch is refused or fails it falls back to a 60s cache. The file viewer header has a refresh button; the pane viewer floats it in the body because a lone pane hides its header

### Code viewer / diff

Ctrl+Shift+E (opens the palette's file entry), or the dock/rail **"파일" tab** (`viewer/tree.js`, `dir.show`). Solves the problem of not being able to see code visually when developing remotely via CLI only. File tree (expand/collapse, address bar, jump to the active terminal's cwd, per-row "insert path into terminal") · syntax highlighting · `git diff` rendering (highlight.js). Tree browsing and git status/diff are two separate dock tabs ("파일" vs "소스컨트롤") — the tree tab carries no git UI, `scm.js` owns that. **Read-only, with no write API.** Since it's exposed over a public tunnel, it has three layers of defense: ① a fixed root (`VT_BROWSE_ROOTS`, default `~/GitHub` — opening `$HOME` would put `~/.ssh`·`~/.aws` in scope) ② `Path.resolve()` + `is_relative_to` (startswith is banned — sibling directories would pass. Since `resolve()` expands symlinks, links pointing outside the root are also caught) ③ a denylist (`.env*`·`*.pem`·`id_rsa`·`.ssh/`·`.aws/` etc., checked against every path component), plus a hidden-directory rule: below the matching browse root, any directory whose name starts with `.` is refused unless it is in the allow set (`.github`·`.gitlab`·`.vscode`·`.devcontainer`·`.husky`·`.storybook`·`.circleci`·`.changeset`·`.worktrees`) — tool state dirs (`.sometool/.auth.json`) stay closed without listing names, and `.git/` is refused too. The root itself and everything above it are exempt (`VT_BROWSE_ROOTS` inside a dot-dir, the auto-added `~/.worktrees` root); dotfiles such as `.gitignore` stay viewable, and the tree/search listings hide the refused directories. The check lives in one place only: `server/fsguard.py`. **Images render inline** — the bytes come from `GET /api/fs/raw`, which adds a type allowlist on top of the same browse boundary (png/jpeg/gif/webp/bmp/ico, and only when extension **and** magic bytes agree). **SVG, HTML and PDF are excluded** — served same-origin they are scriptable documents, i.e. XSS

**File contents render with CodeMirror 6, read-only** (`viewer/editor.js`). The old renderer built one DOM row per line — a 512 KiB file meant about 70,000 nodes and a frozen main thread (2.3 s on a 4x-throttled phone profile); CodeMirror draws only the visible lines and parses incrementally (numbers: [session-view-measurements.md §7](./session-view-measurements.md#7-file-viewer-render-baseline)). `viewer/file.js` `renderFile`/`refreshFile` stay the only entry points (overlay sheet/float and the pane viewer). Details:
- **Chunks.** `editor.js` (view, state, language, search, lezer runtime — about 587 KB raw, 146 KB gzip) is a lazy chunk fetched when a file is opened, in parallel with `/api/fs/file`; each language is its own fixed-name chunk (`editor-js`, `-css`, `-html`, `-md`, `-py`, `-java`, `-go`, `-yaml`, `-json`, `-sql`, `-legacy` for shell/Kotlin/Swift), fetched only for that language. The language comes from `VTDiffLex.langForPath` (unknown extension = plain text). None of it is in the initial payload, and none of it is in `sw.js` PRECACHE: dist chunks are network-first and file contents need the server anyway, so precaching would only add install-time download. If the chunk cannot be fetched the file still shows as plain text (`pre.vt-vw-plain`).
- **Scrolling stays outside.** The editor grows to its content height and CodeMirror finds the scrolling ancestor (`.vt-vw-body`, the pane body), so the consumers' scroll keeping, the pane's sticky refresh/share buttons and the overlay's keyboard focus work as before. Horizontal scroll happens inside the editor and the line-number gutter stays pinned.
- **Refresh changes only what changed.** With an editor showing, `refreshFile` replaces the smallest differing range (`editor-text.js` `textChange`, common prefix/suffix) instead of rebuilding — scroll and selection stay, identical content draws nothing. Image/binary switches and earlier failures still render into a detached host and swap. Editors whose host was dropped (another file opened, pane closed) are destroyed when the next one mounts.
- **Input.** `EditorState.readOnly`. On touch devices (`pointer: coarse`) the content is not `contenteditable`, so tapping never raises the soft keyboard; on desktop it is, so the cursor, select-all/copy and Ctrl/Cmd+F search (CodeMirror's panel, strings through `t()`) cover the whole file — lines that are not drawn are not in the DOM, so the browser's own find only sees the visible part. Esc inside that search panel closes the panel, not the viewer.
- **Colours.** Tokens get `tok-*` classes (`@lezer/highlight` `classHighlighter`) and `styles/screens/30-viewer.css` colours them with the same skin variables as the diff's highlight.js mapping; editor chrome (gutter, search panel, matches) uses tokens too.
- Diff (`viewer/diff.js`) still renders DOM rows with highlight.js and loads it itself (`ensureHljs`; the file view used to load it for both).

### File storage / upload

`~/.vt/files/` (id-based, 0700 dir/0600 files) — there is no path-based upload directory. Uploaded via keybar paperclip (SVG) slot (mobile — stays visible even when the keybar is collapsed) or `Mod+K` → "파일 업로드"; **pasting an image into the terminal uploads it too**. Size cap `VT_MAX_UPLOAD_MB` (default 2048, i.e. 2GB) enforced streaming → 413; total cap `VT_FILES_MAX_GB` (default 5) and `VT_FILES_TTL_DAYS` (default 30) enforced by a cleanup pass on startup + every 6h — files with an active share or `pin` are excluded from cleanup. **Dropping files from the desktop uploads them too** (desktop drag and drop): onto a terminal pane, they upload and the paths are pasted into that pane's session; onto the files panel (dock or pane), they upload and the list refreshes but nothing is typed — you are filing, not typing. Folders are skipped, several files go one request at a time (the endpoint takes one file), and a drop that lands anywhere else is swallowed with a hint instead of letting the browser navigate away to the file and lose the session. All of it, plus the `#file-input` triggers, runs through `frontend/js/term/upload.js` — the one implementation. The `#file-input` element is shared by all upload triggers (keybar, palette, the panel's 올리기 button) — never add a second one. **API is id-only** (`server/file_store.py`) — `GET /api/files/{id}/download` (`attachment`+`nosniff`+`no-store`), `DELETE /api/files/{id}`, `POST /api/files/{id}/insert` (types the path into a tmux pane, no Enter). There is no path-based download API

**Inserted paths are shell-quoted.** The path typed into a pane (upload with `insertPath`, `POST /api/files/{id}/insert`, `fsh files insert`, the 파일 tab's per-row "insert path" — `viewer/tree.js` `pathInsertText`, where the name comes from whatever is inside the browse root: a cloned repository, an unpacked archive) must not contain the file name as is, because the name is chosen by the sender (a paired Mac's `x-peer-file-name`, a received file): `a$(touch x).png` or a backtick/`;` name would run when the person pressed Enter. `shell_quote_path` (`server/shell_quote.py`, mirrored by `frontend/js/lib/shell-quote.js`) leaves paths made of letters, digits, marks and `_@%+=:,./-` alone — ordinary uploads and Korean names pass through unchanged — and wraps anything else in single quotes (`'` becomes `'"'"'`); a first character of `=`, `%`, `-`, `+`, `~` is quoted too (zsh `=cmd`, job specs, options). The server entry point is `tmux_target.type_path_to_tmux`; plain `type_to_tmux` stays for text that is not a path. The same helper quotes the install directory in the hook commands written to `~/.claude/settings.json` and `~/.codex/config.toml` (`claude_hooks.hook_command`, `codex_hooks.hook_command`): a folder with a space or `$` would otherwise break or be interpreted by the shell. **Paths with control characters are not inserted at all.** Quoting only matters once the shell parses the line; the bytes first pass through the tty line discipline, readline or ZLE, which act on `^U` (kill line), `^W`, `\r` (Enter) and the rest no matter where the quotes are — a name like `x\x15touch /tmp/pwn\r` would erase the opening quote and run `touch` before the person pressed Enter (`send-keys -l` and `sendToPty` write raw bytes; a bracketed paste does not help either when the pane has bracketed paste off). So any path with a C0 control character (0x00–0x1F) or DEL (0x7F) is refused at every insert site with a toast or error saying why: `shell_quote.has_control_chars` / `hasControlChars` (`lib/shell-quote.js`), checked in `tmux_target.type_path_to_tmux` (sends nothing, returns False), `POST /api/files/{id}/insert` (400 `unsafe_path` with a reason), `fsh files insert`, the paired-Mac receive (`POST /api/peer/file` — it also types through `type_path_to_tmux` now, so the sender-chosen name is quoted; before it typed the path as is), the upload insert (`term/upload.js` pastes only the safe paths) and the 파일 tab (`viewer/tree.js` `insertPathToTerminal`). Stored upload names already lose control characters (`file_store._safe_name`), so in practice this bites browse-root names. Tests: `test_shell_quote_path.py` (round-trips through a real `sh`; the refusal is checked at the `subprocess.run` that would call tmux), `test_routes_files.py`, `test_routes_peer.py`, `frontend/tests/shell-quote.test.js`, `frontend/tests/viewer-tree-insert.test.js` and `upload.test.js` (the bytes handed to `sendToPty` / the `paste` WebSocket frame).

### Dock attachment tab

dock tab **"첨부"** (also the left rail's paperclip icon and `Mod+K` → "첨부 · 공유 링크"; "파일" is the directory tree tab). Rows carry six actions: download / copy path / insert into terminal / issue link / pin / delete, plus size, upload date+time (`created`, `MM-DD HH:mm` — year prefixed if it isn't this year, full timestamp in `title`) and remaining-TTL text. Chips filter `all|shared|expiring` (expiring = within 3 days) and the footer draws a quota gauge from `GET /api/files`'s `quota`. **Pin** is a toggle (`aria-pressed`) backed by `POST /api/files/{id}/pin` (`file_store.set_pin`, not elevated — same level as delete): a pinned file is kept out of the TTL and total-size cleanup, and its row says 「고정됨」 instead of the time left. Before this there was a `pin` field and a cleanup exemption but no way to turn it on. Issuing a share link is the **first UI path that requires elevation** (`require_elevated`) — a 401 prompts for the password once and retries. **A share token is never returned by the list API** (the list needs no elevation, so a token there would be a way around the elevation gate) — the [복사] button therefore only works for links issued in this browser session. No QR: the frontend carries no QR generator and the dependency isn't worth it (`fsh mobile` already makes QR codes server-side). The renderer lives in the lazy `panels` chunk — importing it into app.js would push the bundle over its 350KiB cap. **Upload progress:** `term/upload.js` uploads via `XMLHttpRequest` (not `fetch` — only `xhr.upload` gives upload-direction progress events) and broadcasts `document` `CustomEvent('vt:upload-progress')` at start/progress/done/error, keyed by a per-call `clientId`. `files.js` can't statically import that module (it's core/store.js vs. the lazy `panels` chunk), so it listens for the same global event instead, the same bridge idiom as `vt:session-switch`/`vt:panel-open`. Progress rows only render while a 첨부 panel instance is open; if none is open the event is just dropped (the completion/failure toast still fires, so nothing is silently lost)

### Share links

`POST /api/files/{id}/share` (elevated) issues a `v1.<exp>.<fileId>.<shareId>.<hmac>` token signed with the same key as session cookies (`auth.sign_payload`) — `GET /s/{token}` is the public entry point, deliberately outside `TokenAuthMiddleware`'s usual gate (`server/routes/share.py` does its own verification). **`device` mode**: requires a registered `vt_device` + valid `vt_session`; missing either → 302 to `/?next=/s/{token}` (login gate redirects back after auth, `frontend/js/gate.js`). **`pin` mode**: static PIN page (no app chrome) → correct PIN sets a 60s one-time download cookie; 5 failed attempts cancels the share. **One-time is enforced on the server:** `file_store.claim_download` checks the cookie's hash and deletes it under the store lock in one step, then the file is sent. It used to only verify and ask the browser to drop the cookie, so the same value worked for 60 seconds, from several requests at once or from a copied cookie. The same claim counts the view and removes a `once` share, so a `once` link (either mode) serves exactly one of several concurrent requests. **Resuming (`Range`):** the claim keeps the consumed cookie's hash on the item (`dl_resumes`: shareId, hash, the cookie's original expiry, `once`) and the download response no longer tells the browser to drop the cookie, so a browser or download manager that resumes a broken transfer gets the rest instead of the PIN page. `routes/share.py` `_try_resume` runs before `_resolve` (a `once` share's record is already gone) and accepts a request only when all of these hold: a single `Range: bytes=N-[M]` with an explicit start `N ≥ 1` and below the file size, the same cookie value (`file_store.claim_resume`), before the cookie's **original** expiry (`DL_COOKIE_TTL`, 60 s after the PIN), the share still exists unless it was a consumed `once` share, and an `If-Range` (if sent) matching the file's ETag/Last-Modified — on a mismatch Starlette's `FileResponse` would drop the range and send the whole file. A resume does not count a view. Everything else falls through to the normal path: a plain re-GET, `bytes=0-`, a suffix range (`bytes=-N`) or several ranges get the PIN page (or 404 for a consumed `once` share), so no new whole download starts without the PIN, and a `once` link never sends the file from byte 0 twice. Trade-off: until that expiry a holder of the cookie value can still fetch bytes 1..end by range — the same 60-second window as before the one-time fix, but only for ranges that skip byte 0. A transfer still running past the 60 s cannot be resumed; the visitor enters the PIN again. Expired `dl_resumes` entries are dropped on the next claim for that file and by the cleanup pass. **The limit is atomic:** `file_store.reserve_pin_attempt` reads the share and bumps `attempts` under the store lock *before* the PIN is checked. Judging from a snapshot taken at the start of the request would let parallel requests all see `attempts=0` and all be verified, defeating the limit. Each wrong guess also counts toward the pre-auth source lockout (`share_pin`), the form body is read through a 4KB cap (413 above it; buffering the whole body on a pre-login route is not acceptable), and **new** PINs must be 6–20 characters (`MIN_PIN_LEN`; `fsh files --pin` generates 6 hex characters). Tests: `test_share.py` (including concurrent and replayed cookies, concurrent `once` downloads, `Range` resume within and after the window, refused plain/whole-file re-requests, `once` resume), `test_file_store.py` (`claim_resume`). Store calls on these routes and on `/api/upload` run in a thread (`asyncio.to_thread`) — the store's flock waits up to 5 s while the CLI holds it, which on the event loop froze the whole server; `test_no_blocking_in_async.py` lists the `file_store` calls. Cancelling (`DELETE .../share/{shareId}`) removes the record from `files.json` — the URL 404s immediately even though the signature is still cryptographically valid. `once` shares self-delete after the first successful download. The Files panel provides share issuance and revocation controls

### Sharing from the 파일 tab (snapshot import)

Share links only attach to file-store (id) files, and there is deliberately no path-based download API. So the 파일 tab row button, the viewer header button (sheet/float) and the pane viewer's floating button call `POST /api/fs/share-import {path}` (`routes/share.py`, elevated): `fsguard.resolve_under_roots` (root, denylist, hidden dirs), then the file is opened with `fsguard.open_resolved`: the resolved path is walked from `/` one component at a time with `O_DIRECTORY|O_NOFOLLOW` relative to the previous directory fd, the last component with `O_NOFOLLOW|O_NONBLOCK`, and checked regular via `fstat`. A symlink swapped in after `resolve()` — for the file **or any parent directory** — fails with `ELOOP`/`ENOTDIR` (400 `not_a_file`); plain `O_NOFOLLOW` only covers the last component, so a parent swapped for a link to outside the root used to copy that outside file. Symlinks that were inside the root at check time still work, because `resolve()` already expanded them. The file is then size-capped by `VT_MAX_UPLOAD_MB` while streaming, and copied into the store with `origin=fs:<path>:<size>:<mtime_ns>`. The same unchanged source reuses its snapshot; a changed source makes a new one. The snapshot does not follow later edits to the original, and the dialog says so. Then `openShareDialog` (same dialog as the 첨부 tab) issues the link; elevation is asked once and retried.
