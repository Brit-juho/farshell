# Files, sharing, code viewer

## Features

### File viewer surface

`viewer.surface` setting (Settings → 모양): `sheet` (default) / `float` / `pane`. `sheet`/`float` are overlays mounted inside `#terminal-container` (`panels/viewer/overlay.js`) — opening/closing a file does not resize the pane tree, so xterm never `fit()`s and no `SIGWINCH` reaches vim/tmux/less (a pane-leaf viewer would resize the tree). The overlay's click-through background lets you keep typing in the terminal with the file open; Esc only closes it when focus is inside the card (terminal-focused Esc still reaches vim). `sheet` drags its height (`viewer.sheet.height`, 20–85%) with the shared `wireRatioResizer`; `float` drags position/size (`viewer.float.rect`, a JSON rect, clamped so it can never end up off-screen with no way back). A header button ("페인으로") switches to the `pane` surface for side-by-side reading. `openFileInPane()` opens a pane leaf (used by the overlay header's "페인으로 열기" button); `openFile()` is the default entry point everything else calls, and branches on the setting. Compact (<720px) ignores the setting and always opens a fullscreen sheet with back-button close. All three surfaces share the same renderer (`viewer/file.js:renderFile`) — content code is one copy regardless of surface

### Auto-refresh (`/ws-fs-watch`)

The open file (every surface), the 파일 tree (one `tree` subscription on its root — [File tree](#file-tree-파일-activity-vt-dir)) and the 소스컨트롤 tab's change list redraw when the disk changes. `shell/fs-watch.js` subscribes (it lives in the `shell` chunk so the viewer and the rail's git badges share one connection — `core.js` has no room under its initial-payload cap (350KiB for app.js + core.js), and `shell` is loaded at boot anyway; `file` / `dir` / `repo` / `tree`, full list on every change, connection only while something is subscribed, re-reads everything once after a reconnect); `server/fs_watch.py` answers with "this subscription changed" only (the one exception: a `tree` notice also lists the changed folders, relative to the root, at most 200 or `overflow`, never a folder the tree hides or a deny-listed name) — the redraw goes back through `/api/fs/*`·`/api/git/*`, so the browse boundary is unchanged. Subscriptions go through `fsguard.resolve_under_roots`, deny-listed names never trigger. `file` watches the **parent** directory (editors save by rename, which breaks an inode watch). `repo` is widened to the work-tree top and refused outside a git repo (otherwise a session sitting in `~/GitHub` would watch all of it); inside `.git` only `index`/`HEAD`/`refs/` count, so `git status` touching `index.lock`/`objects` cannot trigger itself. All connections share **one flat and one recursive** `watchfiles` watcher — each `awatch` holds a thread from anyio's default pool (40, shared with Starlette's sync routes), so a watcher per connection would eat it. Redraws keep scroll, expansion, the selected row and a half-typed commit message; the source-control tab only redraws while its list is showing, never over an open diff. The rail/fleet git badge also uses `repo` subscriptions: while a cwd's watch is live the count is re-read only after a change (at most every 30s, and once every 10 min as a safety net); if the watch is refused or fails it falls back to a 60s cache. The file viewer header has a refresh button; the pane viewer floats it in the body because a lone pane hides its header

### File tree (파일 activity, `vt-dir`)

The sidebar's 파일 activity (also `dir.show` from the palette, and a pane leaf when the activity is dragged into a pane) is a Solid + TypeScript tree in `frontend/js/files/` (lazy chunk `files`, about 60 KB / 16 KB gzip). `panels/viewer/tree.js` keeps only the panel shell and its contract: panel id `vt-dir`, `showTree(opts)` (`opts.paneHost` for a pane), the 「경로 삽입」 quoting (`pathInsertText`/`insertPathToTerminal`) and `_viewerState.root` for the source-control tab's fallback.

- **Flattened rows + virtual scroll.** `tree-model.ts` `flatten` turns the loaded folders into one row array; only the visible rows plus 10 above and below (`windowRange`, `OVERSCAN`) are in the DOM, positioned with `transform`. Row height is one variable: 28px, 22px with the device setting `files.tree.dense` (Settings → 모양 → 파일 트리 촘촘하게), 44px on a phone (<720px) whatever the setting.
- **Diffed by path key.** Every row is keyed by `(hostId, path)`; a per-folder cache (`FlattenCache`, invalidated by the store's `expandVer` per folder and `marks` for change marks) rebuilds only the folder that changed and its ancestors and hands back the **same row objects** for everything else, so `<For>` keeps their DOM. With a name filter on, rows are rebuilt and matched back by key (`reuseRows`).
- **Delegated events.** The scroll box is the only listener (click, context menu, pointer, keys); rows carry `data-key` and the hover buttons `data-act` (insert / share / menu).
- **Keyboard and aria.** The scroll box is `role="tree"` and owns focus; `aria-activedescendant` points at the focused row (a virtual row can leave the DOM). Rows are `treeitem` with `aria-level`, `aria-expanded`, `aria-selected`, `aria-setsize` (the server's `total`, so paging does not shrink it) and `aria-posinset`. Keys (`treeKey`): ↑↓, → expand / first child, ← collapse / parent, Home/End, Enter·Space open or toggle, ⌥Enter insert path, ⇧F10 or the menu key opens the row menu, `/` focuses the filter, typing jumps to the next name with that prefix (`typeahead`).
- **Name filter.** Substring (case-insensitive, the match is highlighted) or a glob when it contains `*`/`?` (`*.tsx`). It looks only at names already loaded — every loaded folder, collapsed ones included, shown open while filtering — not the disk; the palette's `/` mode searches the disk.
- **Paging.** A folder shows its first page (1000) and a 「더 불러오기 · N개 더」 row (`after=` cursor, `/api/fs/tree`, [API.md](../../API.md)); past the server's 50,000 scan cap a note row says only that many were listed.
- **Fetch rules.** Opening a root asks `depth=2` once; expanding an unloaded folder asks `depth=1`; a prefetched folder expands without a request.
- **Change watch (`tree` kind).** One recursive subscription on the tree root replaces the per-folder `dir` subscriptions (64-per-connection cap, and no way to tell which folder changed — a root change refetched every expanded folder, 101 requests with 100 open). A notice carries the changed folders; a visible (root-to-folder expanded) loaded folder is re-read with `depth=0`, as many pages as were loaded, and diffed against the old listing: new entries and files whose size or `mtime` changed get a dot (`--color-st-done`, 6px), their ancestor folders a ring; opening the file clears its dot. A loaded folder that is not visible is dropped and marked (ring) instead of re-read. `overflow`, a reconnect, or the header refresh button re-read every visible loaded folder. A remote host's server that predates `tree` ignores the kind (it is not rejected), so such a tree only refreshes by the button.
- **State keyed by host.** `TreeStore` keys every map by `(hostId, path)` (`relayHost()`); opening another root bumps an epoch and late answers for the old root are dropped. The host line shows the host label from `/api/hosts`.
- **Row menu.** 열기 (펼치기/접기 for a folder) · 터미널에 경로 삽입 (`insertPathToTerminal`: shell quoting, control characters refused) · 경로 복사 · 다운로드 (files) · 공유 링크 만들기 (files) · 이 폴더에 새 파일… · 이름 바꾸기… (files) · 휴지통으로 이동… (files) · 새로고침 (that folder). The write items ([Editing and file writes](#editing-and-file-writes)) stay visible on a remote host with 「이 컴퓨터에서만」 and only explain why when chosen; after a write the folder is re-read. On a phone a long press (500 ms) opens the same items as a bottom sheet (44px items); the menu is portalled to `body` so the bottom nav cannot cover it.
- **Phone entry.** The bottom nav's 4th tab is 「파일」 (folder icon, `mfiles.show`); it opens the side last shown, remembered in the device setting `ui.mobile.filesSegment` (`tree` default / `attach`). Both the tree (`vt-dir`) and attachments (`vt-files`) are tab screens there and get a 「파일 | 첨부」 segment under their header (`layout/mobile-nav.js`); the upload badge stays on the tab (`#vt-mnav-badge-files`) and is repeated on the 첨부 side of the segment. The 변경 tab has no segment.

### Content search (palette `?`, sidebar 「내용 검색」)

Finds text **inside** files (`GET /api/fs/grep`, contract in [API.md](../../API.md)). Two entry points share one screen, `frontend/js/shell/GrepView.tsx` (shell chunk), and one engine:

- **Palette `?` mode.** `?` followed by the text (`? groupByZone`; to find text that starts with `?`, type it twice: `? ?.`). The palette widens to 1100×720: an options row (match case ⌥C · whole word ⌥W · regex ⌥R, include and exclude globs, the scope folder), a progress row (elapsed time, 「취소」, a 2px bar — the only moving thing), results grouped by file (`groupByFile` in `grep-data.ts`: file header with folder and count, 24px lines with the line number and the match marked in `--color-term-hl`), a skipped-files note, and on wide screens a 460px preview of the selected line's surroundings (`/api/fs/file`, cached per file). ↑↓ move, ↵ opens the file **at that line** with `openFile(path, {line, col, host})`, ⌘↵ opens it in a new pane, ⌥↵ moves the same query and options to the sidebar. The scope is the active session's repository root (`context.root`, else its cwd); if that is outside the browse boundary it falls back to every start root.
- **Sidebar 「파일 › 내용 검색」.** The 파일 activity has a 「트리 | 내용 검색」 segment (`files/mount.tsx`); the search side has a query box with the three toggles, include and exclude boxes, a header with the summary, 「다시 찾기」 and 「모두 접기」, and results that fold per file. Its scope is the tree's current root. The tree stays mounted (hidden) while the search side is shown.
- **Shortcut.** `contentSearch` — ⌘⇧F on macOS, Ctrl+Shift+G elsewhere (Ctrl+Shift+F is scrollback search) — opens the sidebar search (on a phone, the palette `?` mode instead). `palette-lazy.js` leaves the request in `window.__vtFilesSearchPending` and calls `dir.show` when the panel is closed, or sends `vt:files-search` when it is open. In-terminal search (`searchInPane`) moved from ⌘⇧F to Alt+Shift+F on every platform; a binding the user set keeps working, and `keymap.match` tries user-set combos before defaults, so a user who had pinned ⌘⇧F keeps it. The first ⌘⇧F on a Mac shows a one-time toast about the move.
- **Requests.** Typing debounces 250 ms; a new query aborts the previous `fetch`, and the server cancels the previous search for the same client (`sid`, one per screen) and kills its process when the connection drops. The browser deadline is 25 s (server deadline 10 s plus relay slack) so a timed-out search still arrives with its partial results.
- **States** (F06-B): result/size limits and the deadline are said on the progress row in `--warn` with what was found; a regex error shows the server's reason (character position) and 「검색하지 않았습니다」; 503 says the search can't run now with 「다시 시도」 (file-name search `/` still works); no result offers 「제외 없이 다시 찾기」 when an exclude was set. The number of deny-listed files skipped is never shown.
- **Engine and safety** (`fs_grep.py`, `scan_worker.py` `grep` mode). Candidates come from `git ls-files --cached --others --exclude-standard` inside a work tree (`.gitignore` respected; `git_safe` flags) or the filename-search walk outside one. Skip prefixes (risky mounts, File Provider / iCloud folders, quarantined scan paths) inside the search root are passed to git as `:(exclude,literal)<rel>` pathspecs, so git never walks them (a home folder that is a repo would otherwise walk `~/Library`); a root inside a skip prefix lists nothing and git is not started. Deny-listed names, deny folders, hidden folders, excluded folders and risky mounts are removed from the list **before** any file is read — a secret that was committed by mistake is still never opened. Files are opened one path component at a time from the root's fd (`_Opener`, the same walk as `fsguard.open_resolved`: folders with `O_DIRECTORY|O_NOFOLLOW`, the file with `O_NOFOLLOW`) and must be regular files, so neither a symlink in the tree pointing at `~/.ssh/id_rsa` nor a crafted index entry that goes through a folder symlink (`sub/secret` with `sub` → outside) is read — otherwise the result would be dropped later but `dropped` would still tell whether the text exists outside. Folder symlinks are not followed. Every result file is re-checked with `resolve_under_roots` before it is returned. Each line keeps at most `max_ranges` (20) matches and the rest of that line is skipped, so `.` on a 2 MB line does not collect two million spans. Python `re` has no timeout, so regex mode is bounded by the child process's deadline; regexes that match empty text are refused. Results on another host come from that host (relayed; its boundary and deny rules apply).

Not yet: a 「결과가 오래됨 · 다시 찾기」 banner when a watched file changes under sidebar results, and a determinate progress bar (the server answers once; progress is elapsed time).

### Code viewer / diff

Ctrl+Shift+E (opens the palette's file entry), or the sidebar's **"파일" activity** (the tree above, `dir.show`). Solves the problem of not being able to see code visually when developing remotely via CLI only. File tree (see above) · syntax highlighting · `git diff` rendering (highlight.js). Tree browsing and git status/diff are two separate dock tabs ("파일" vs "소스컨트롤") — the tree tab carries no git UI, `scm.js` owns that. **Reading needs a login; writing (save, new file, rename, trash) also needs a re-typed password and a human session — see [Editing and file writes](#editing-and-file-writes).** Since it's exposed over a public tunnel, reading has three layers of defense: ① a fixed root (`VT_BROWSE_ROOTS`, default `~/GitHub` — opening `$HOME` would put `~/.ssh`·`~/.aws` in scope) ② `Path.resolve()` + `is_relative_to` (startswith is banned — sibling directories would pass. Since `resolve()` expands symlinks, links pointing outside the root are also caught) ③ a denylist (`.env*`·`*.pem`·`id_rsa`·`.ssh/`·`.aws/` etc., checked against every path component), plus a hidden-directory rule: below the matching browse root, any directory whose name starts with `.` is refused unless it is in the allow set (`.github`·`.gitlab`·`.vscode`·`.devcontainer`·`.husky`·`.storybook`·`.circleci`·`.changeset`·`.worktrees`) — tool state dirs (`.sometool/.auth.json`) stay closed without listing names, and `.git/` is refused too. The root itself and everything above it are exempt (`VT_BROWSE_ROOTS` inside a dot-dir, the auto-added `~/.worktrees` root); dotfiles such as `.gitignore` stay viewable, and the tree/search listings hide the refused directories. The check lives in one place only: `server/fsguard.py`. **Images render inline** — the bytes come from `GET /api/fs/raw`, which adds a type allowlist on top of the same browse boundary (extension **and** magic bytes must agree). Markdown, SVG, CSV, video/audio and PDF have their own previews — see [Previews and downloads](#previews-and-downloads). **HTML and PDF bytes are never served for viewing** — served same-origin they are scriptable documents, i.e. XSS

**File contents render with CodeMirror 6, read-only until 「편집」** (`viewer/editor.js`; editing is described below). The old renderer built one DOM row per line — a 512 KiB file meant about 70,000 nodes and a frozen main thread (2.3 s on a 4x-throttled phone profile); CodeMirror draws only the visible lines and parses incrementally (numbers: [session-view-measurements.md §7](./session-view-measurements.md#7-file-viewer-render-baseline)). `viewer/file.js` `renderFile`/`refreshFile` stay the only entry points (overlay sheet/float and the pane viewer). Details:
- **Chunks.** `editor.js` (view, state, language, search, lezer runtime — about 587 KB raw, 146 KB gzip) is a lazy chunk fetched when a file is opened, in parallel with `/api/fs/file`; each language is its own fixed-name chunk (`editor-js`, `-css`, `-html`, `-md`, `-py`, `-java`, `-go`, `-yaml`, `-json`, `-sql`, `-legacy` for shell/Kotlin/Swift), fetched only for that language. The language comes from `VTDiffLex.langForPath` (unknown extension = plain text). None of it is in the initial payload, and none of it is in `sw.js` PRECACHE: dist chunks are network-first and file contents need the server anyway, so precaching would only add install-time download. If the chunk cannot be fetched the file still shows as plain text (`pre.vt-vw-plain`).
- **Scrolling stays outside.** The editor grows to its content height and CodeMirror finds the scrolling ancestor (`.vt-vw-body`, the pane body), so the consumers' scroll keeping, the pane's sticky refresh/share buttons and the overlay's keyboard focus work as before. Horizontal scroll happens inside the editor and the line-number gutter stays pinned.
- **Refresh asks first, then changes only what changed.** `refreshFile` sends the first range again with `If-None-Match` (the ETag of the version on screen, `core/api.js` `vtFetchConditional` — same deadlines, reachability accounting and host relay as `vtFetch`, but a 304 is a success with no body). 304 → nothing happens. 200 → the same extent is read again and the editor gets the smallest differing range (`editor-text.js` `textChange`, common prefix/suffix) instead of a rebuild — scroll and selection stay, identical content (a save that only touched mtime) draws nothing. Image/binary switches and earlier failures still render into a detached host and swap. Work on one viewer runs one at a time (`_serial`): the **whole open** (first range, continuation ranges, the line jump's extra load), refresh, 「더 보기」 and line jumps. A refresh that arrives while an open is still appending waits for it — before, it could replace the document after the first range and the open then appended its remaining ranges after that, so the end appeared twice.
- **A big view refreshes only what grew.** When more than 256 KB is on screen (`INCREMENTAL_MIN`; less is cheaper to re-read whole), a refresh first asks for the 8 KB just before the loaded end (`PROBE_BYTES`, `loadProbe`; conditional when it is the same window as last time, so an unchanged file costs one 304). `file-load.js` `growthFrom` accepts the reply as "only grew" when the size went up, `rev`'s `dev:ino` is unchanged (a save by rename is a new file), the window ends on a line end exactly where the screen's text ends (minus the bytes of an unterminated last line — countable only for confident UTF-8; other encodings need a terminated last line) and the window after its first line end equals the same text on screen (`\n` is never part of another character in the supported encodings, so a window that starts mid-character decodes the same after it). Then only the bytes after the old end are read (`expected_rev` pinned to the window's rev; an unterminated last line is read again and replaced) and appended — a growing 4 MB build log costs a few KB per change instead of 4 MB. If more was on screen than the file had (`eof` false), nothing is read and only the total in the bottom note changes. Anything else — size not grown, window different, other inode, 409, a window the server refuses — falls back to the full re-read above. Not seen: an edit before the window that also grows the file while the window stays identical (rev is metadata); the refresh button after a reopen, or the next full re-read, catches up. The tail view uses the same path and follows the new end; once it holds more than 2 MB it reopens as a fresh 1 MB tail.
- **Auto-refresh of big views is spaced.** `coalesce(fn, {minGap})` (`shell/fs-watch.js`) runs the first notice at once and folds the ones that arrive within the gap into one run after it; `file.js` `refreshGap` gives 1 s when more than 1 MB is on screen, 0 otherwise. The overlay and the pane viewer use it; the tree and source-control tabs do not.
- **Editors are destroyed when their viewer goes away.** CodeMirror registers listeners on `window` and the scroll ancestor, so a detached editor stays alive. `disposeViewer(root)` destroys the editors under `root` and cuts the viewer's state so an open in flight stops drawing (an editor mounted after that is destroyed at once). It is called when the overlay closes or shows another file, when a refresh swaps the host, and from `layout/panes.js` when a viewer pane changes to something else or leaves the tree (`_sweepViewerBodies` after each full render — closing the pane, or moving away in compact mode, where the pane is rebuilt when you come back). Mounting a new editor still sweeps any detached leftovers.
- **Loading in ranges** (`viewer/file-load.js`, pure, no DOM). A file is read in 1 MB ranges up to the first 4 MB (`OPEN_BUDGET`); the first range is drawn as soon as it arrives and the rest are appended at the end of the document, so scroll and selection are untouched. Continuation ranges pin the encoding of the first reply (`auto` judges each reply on its own; `unknown` was decoded as UTF-8 with replacement, so it continues as `utf-8`) and send `expected_rev`; a 409 restarts from the beginning, and three in a row stop with 「파일이 계속 바뀌는 중」 in the top bar, keeping what was on screen (the next change notice or the refresh button tries again). A range that ends in `\r` holds it back for the next one, so a CRLF split by a `line_truncated` cut does not become two lines.
- **Bigger than 4 MB.** The bottom note says how much is loaded out of the total and that find / go-to-line only cover the loaded part (lines that were never fetched cannot be searched — whole-file search is the server-side search of a later step). 「더 보기」 appends the next 4 MB, up to 64 MB per viewer (`MAX_LOADED`; larger caps risk the tab being killed on phones); past that the note says so and 「끝부분 보기」 is the way to the end. A long last line cut by the window adds 「마지막 줄이 길어 중간에서 끊겼습니다」; a single line longer than 1 MB inside the budget is joined from its ranges and shown whole.
- **End of the file (tail).** 「끝부분 보기」 reads the last 1 MB from its first line start (`tail=`). Line numbers are unknown there, so the gutter counts from the end (`-1` is the last line; `mountEditor(..., {lineFrom: 'end'})`) and the top bar says so; if the window has no line start it also says the view begins mid-line. A refresh is conditional too, and when the view was scrolled to the end it follows the new end, like `tail -f`. 「처음부터 보기」 goes back.
- **Encoding and the read-only reason (D9).** The top bar appears only when there is something to say: a reply that is not confident (`encoding_reason` `not_utf8` / `guessed_utf16` / `decode_errors`) or mixed line endings (CRLF with LF or CR, detected on the raw ranges) show 「읽기 전용 · <reason>」 — these are the files a later editor will refuse to save — plus an encoding select (`auto` and the eight API encodings; `auto` shows what it resolved to). Choosing one reopens the viewer in place; the choice is remembered per (host, path) for this page. A `suggested` encoding different from the one shown gets a one-click button.
- **Line jumps from the terminal.** `term/links.js` splits `path:line:col` (`link-scan.js` `splitPathLine`) and calls `openFile(path, {line, col, host})`. The editor moves the cursor there, centres it and marks the line (`.cm-vt-target`, needed on touch where the cursor is hidden). A line past the loaded part loads at most one more 「더 보기」 (4 MB), and only when the average line length so far puts the line inside it — so `foo.log:99999999` does not pull 64 MB; otherwise a toast points to 「더 보기」 and 「끝부분 보기」 (or says the line is past the end of a fully loaded file). Re-opening the file that is already showing only jumps. The pane surface gets the jump through `queueJump` (the pane is drawn from layout state, which has no place for a line).
- **The session's host, not the selected one.** A link in a remote pane (`session.remote.host`, `term/host-view.js` `hostOfSession`) is opened on that host: the relative path is resolved against that host's tmux cwd, `~` against its home, and the file is read through `/api/hosts/<id>/relay/api/fs/file` (`file-load.js` `hostApiPath`; images through the same relay). Such a file always opens in the overlay (pane leaves do not store a host yet), is not added to recent files (they store paths only), has no share button (sharing snapshots a path on this host) and is not auto-refreshed (the watch socket belongs to the screen's host; the refresh button works). Per-host keys for watching and recent files are part of the tree rewrite.
- **Input.** `EditorState.readOnly`. On touch devices (`pointer: coarse`) the content is not `contenteditable`, so tapping never raises the soft keyboard; on desktop it is, so the cursor, select-all/copy and Ctrl/Cmd+F search (CodeMirror's panel, strings through `t()`) cover the whole file — lines that are not drawn are not in the DOM, so the browser's own find only sees the visible part. Esc inside that search panel closes the panel, not the viewer.
- **Colours.** Tokens get `tok-*` classes (`@lezer/highlight` `classHighlighter`) and `styles/screens/30-viewer.css` colours them with the same skin variables as the diff's highlight.js mapping; editor chrome (gutter, search panel, matches) uses tokens too.
- Diff (`viewer/diff.js`) still renders DOM rows with highlight.js and loads it itself (`ensureHljs`; the file view used to load it for both).

### Editing and file writes

Files-overhaul step 8 (decisions D1, D2, D3, D7, D9). Server: `server/fs_write.py`, `server/fs_trash.py` (+ the macOS helper `fs_trash_macos.py`), routes `server/routes/fs_write.py`; contracts in [`API.md`](../../API.md) (`PUT /api/fs/file`, `POST /api/fs/new`, `/api/fs/rename`, `/api/fs/delete`). Client: `panels/viewer/edit.js` (edit mode), `fs-write.js` (requests and the new / rename / trash dialogs), `editor.js` (`setEditable`).

**Threat model.** These are the first routes that change files over a public tunnel. What stops a write that should not happen:
1. **Who:** the router requires a human browser session **and** elevation (`require_human_session` + `require_elevated`, [auth.md «Elevated actions»](./auth.md#elevated-actions)). A machine token, an agent over the unix socket, a peer, a cookie sent together with a token, a cross-site page (`OriginGuardMiddleware`) and a server without a password are all refused. Agents write with their own tools; leases are only a notice here (`lease.override` is audited).
2. **Where:** `fsguard.resolve_for_write` is the only place that decides (contract 2): absolute path, no `..`, no control characters; then every read rule (`resolve_under_roots`: browse boundary, deny list, hidden state folders); then the write-only rules — no component named `.github` `.gitlab` `.husky` `.devcontainer` `.vscode` `.circleci` (readable, but CI/hook/task configuration that runs code) or `.git` (a gitfile pointing elsewhere makes the next git command use another repository's hooks and `core.fsmonitor`), compared case-insensitively because the default macOS disk ignores case; finally inside `VT_WRITE_ROOTS` (a boundary key; empty = the browse boundary, `off` = no writes, never wider than the browse boundary).
3. **The path cannot change under the check:** everything is done relative to the parent folder's fd from `fsguard.open_resolved_parent` (one component at a time with `O_NOFOLLOW`): the temp file (`O_CREAT|O_EXCL|O_NOFOLLOW`), `rename(src_dir_fd=, dst_dir_fd=)`, `link`, the Linux trash move. A parent swapped for a symlink after the check fails with `ELOOP`/`ENOTDIR`; a last component swapped for a symlink is opened with `O_NOFOLLOW` and refused. Tests swap them in the middle of each operation and check that nothing outside the root changed.
4. **What may be replaced:** `rename` over a file only needs write access to the folder, so it would also replace read-only files and other users' files; the server refuses unless the file is yours, has the owner-write bit and no immutable/append flag. Hard-linked files (`st_nlink > 1`) are refused (replacing would split them). Folders and symlinks cannot be renamed or trashed in this round.
5. **Where it ends up:** delete never unlinks — it moves to the OS trash or refuses.
6. **Remote hosts:** not in the relay allowlist on either side (decision D7); the UI keeps the buttons visible but dimmed with the reason.

**Save** (`fs_write.save`). Under a per-(parent dev, parent inode, casefolded name) lock: open the target from the parent fd, compare `rev` with `expected_rev` (409 `conflict` with the current rev), refuse hard links / other owner / read-only / over 2 MB, read the current bytes and require them to decode strictly in the requested encoding with one kind of line ending (D9 — the same files the viewer already shows read-only), convert the editor's LF text to the file's line ending and BOM, encode strictly (422 `unencodable` with the line/column of the first bad character), write `.fsh-<uuid>.tmp` in the same folder with the original mode (`fchmod`; the group is kept when `fchown` is allowed), `fsync`, check the rev again, `rename`, `fsync` the folder (`durable:false` if only that fails). Two saves through this server with the same `expected_rev`: one wins, the other gets 409. `save_id` results are kept 10 minutes (`fs_write.SAVES`, keyed with the device and a fingerprint of the request): a retry after a timeout returns the first result (`replayed:true`) instead of writing twice — `fsops` deadlines do not stop the worker thread, so the first save may still finish. **Not covered:** an external editor writing between the final rev check and the `rename` (a very short window; Paseo and Orca have the same one); ACLs and extended attributes are not copied (macOS Python has no `os.listxattr`), and the owner is never changed (other owners are refused instead).

**New file** (`fs_write.create`): Paseo's name rules (not empty, no `/` `\` NUL or control characters, not `.`/`..`, ≤255 bytes), deny-listed names refused, created empty with `O_EXCL` from the folder fd — an existing name, including a symlink, is never overwritten. **Rename** (`fs_write.rename`): one regular file, both ends checked by `resolve_for_write`, same disk only; no overwrite unless `overwrite:true` (and then only a regular, non-hard-linked file of yours); without it the move is `link` then `unlink` of the old name, which fails atomically on an existing name (file systems without hard links fall back to check-then-rename under the lock).

**Trash** (`fs_trash`, decision D2).
- **macOS:** `NSFileManager trashItemAtURL:resultingItemURL:error:` called through ctypes in a **separate process** (`python -I fs_trash_macos.py <path>`, 15 s deadline via `resilience.proc`). JXA (`osascript -l JavaScript`) crashed with SIGSEGV on the out parameters, and Finder over AppleScript needs an Automation permission prompt that can block a server; a crash in the helper cannot take the server down. It is the Finder path: the trash folder's `.DS_Store` gets the original location (`ptbL`) and name (`ptbN`), which Finder's 「되돌리기」 (Put Back) reads; name clashes become `name 16-10-17-901.txt`. A file on another volume goes to `<volume>/.Trashes/<uid>`. The helper takes a path, so the server checks right before that the path still names the inode it checked through the folder fd, and afterwards that the item in the trash is that same inode (else 500 `trash_mismatch` — it is in the trash, not lost). Verified on an APFS disk image: the file moved to `.Trashes/501` and the `.DS_Store` held `ptbL`/`ptbN` for it (the Put Back click itself was not automated). **`HOME` does not redirect it:** `NSFileManager` resolves the boot volume's trash from the account, not `$HOME`, so a test that must not touch the real `~/.Trash` uses a file on another volume (`tests/e2e` `VT_E2E_TRASH_DIR` on a disk image).
- **Linux / WSL:** freedesktop.org Trash spec 1.0, in Python. Same device as `$XDG_DATA_HOME/Trash` (default `~/.local/share/Trash`) → there, `Path=` absolute; otherwise the mount's top folder: `.Trash/<uid>` when `.Trash` is a real folder with the sticky bit, else `.Trash-<uid>` (0700), `Path=` relative. `info/<name>.trashinfo` (`Path=` percent-encoded, `DeletionDate=` local time) is created first with `O_EXCL` to claim the name (`name.2.ext`, … on clashes), then the file is `rename`d from the checked folder fd into `files/`; if that fails the `.trashinfo` is removed. The trash folder must belong to you.
- **Anything else** (other OS, no trash on that volume, permission, read-only, another device) → 409 `trash_unavailable`. There is no fallback to deleting.

**Edit mode** (`edit.js`, mockups F05–F05-G, M-F5). 「편집」 in the viewer's top bar (`.vt-vw-bar`) switches the **same** `EditorState` to editable (`editor.js` `setEditable` reconfigures a compartment: history, default keys, Tab indent, `Mod-s`; all in the lazy `editor` chunk with `@codemirror/commands` — the initial payload is unchanged). Allowed when: this computer's file, the source view, the whole file loaded (`eof`), ≤ 2 MB, a confident encoding, one kind of line ending, not 「계속 바뀌는 중」; otherwise the button is dimmed with the reason. While editing the bar shows the state (편집 중 · 저장 안 됨 with a `--color-st-waiting` dot, 저장 중…, 저장됨 HH:MM, 저장 실패, 충돌), the one primary button 「저장」 (⌘S / Ctrl+S, also with focus on the bar) and 「편집 끝내기」 (asks before discarding, focus on 취소); the bar is sticky inside the scroll box, so on a phone 「저장」 stays visible above the soft keyboard. Requests are cookie-only (`writeFetch`: no `?token=`, no `Authorization`, no host relay) with the normal deadline; 401 `elevation_required` → the password dialog (`authz/elevate.js`) → the same request again; 503 / timeout → once more with the same `save_id` (a `replayed` answer says so). Failure toasts follow the failure contract (507, 403, 422 with a jump to the line, 413, 409 `hardlinked`, `durable:false`); the edit and the dirty state stay. **Outside changes:** a refresh (watch notice or button) while editing goes to `refreshEditing` instead of replacing the document — a rev equal to the one just saved is ignored, the same text is ignored, an unedited buffer follows the disk, and an edited one gets the conflict banner (비교 — a line diff of disk vs. edit around the changes; 다시 불러오기; 내 것으로 덮어쓰기, which saves with the disk's current rev; both destructive actions confirm). A file deleted elsewhere offers to recreate it (`expected_rev: null`, no overwrite). **Leaving with edits:** when a viewer goes away (close, another file, pane removed, surface change, reopen with another encoding) `disposeViewer` keeps the unsaved text, base and rev by (host, path); opening that file again resumes editing, with a conflict banner if the disk moved on. A page unload with unsaved edits triggers the browser's leave prompt. Tests: `server/tests/test_fs_write.py`, `test_fsguard.py`, `test_peer_relay.py` (writes refused on both sides), `frontend/tests/viewer-edit.test.js`, `files-tree.test.js`, browser smoke `tests/e2e/test_smoke.py` (edit → ⌘S → password → saved; follow, conflict, compare, overwrite; new, rename, trash).

**Not done yet:** folders (new, rename, trash), remote writes (need elevation through the relay), changed-line marks in the gutter, the 「저장 / 버리기 / 취소」 dialog on close (edits are kept instead), the phone's accessory key row and hiding the bottom tabs while editing, and the real-device IME check (Android Gboard Hangul).

No size cap — the browser fetches what it plays.
- **PDF** (decision D8): never previewed — the browser's PDF viewer can run document scripts. An empty state explains why with one download button. Other binaries show the same download button.
- **Streaming from the checked fd.** `/api/fs/raw` and `/api/fs/download` open the file once (`resolve_under_roots` + `open_resolved`, inside `fsops`), then stream 256 KB chunks from that fd (each read in `fsops`, retried briefly on pool `Busy`). Each chunk re-checks the fd's rev; a change mid-send ends the stream with an error so the client sees a cut-off transfer, not a mixed file. The fd is closed when the stream ends, fails or the client goes away — including a client that disconnects while the headers are being sent, before the body generator ever starts: the reply class (`fs_stream.FdStreamingResponse`) closes it in its own `finally`, and everything between the open and handing over the reply is wrapped to close it too. `fs_stream.close` is idempotent (a second call must not close a reused fd number). An open that finishes after its deadline closes its own fd (`_Holder`). `Range` numbers are ASCII digits only (`str.isdigit()` accepts `²`, which `int()` refuses); a number longer than 19 significant digits is treated as larger than any file, never passed to `int()`. Only `GET` is routed (no `HEAD`).
- **Downloads** (decision D4/D7, `GET /api/fs/download?path&rev`). ### Reading files: versions, ranges, encodings (`/api/fs/file`)

The contract is in [`API.md`](../../API.md); the code is `server/fs_read.py`, called from `routes/files.py` inside `fsops.call` (the `fs` pool, `VT_FS_TIMEOUT`, path breaker — path check, open and read never touch the event loop).

- **One fd for everything.** After `fsguard.resolve_under_roots`, the file is opened with `fsguard.open_resolved` (one component at a time, `O_NOFOLLOW`); size, kind, `rev` and content all come from that fd (`fstat`, `pread`). Re-opening the path would reopen the check-then-open gap. A file or parent directory swapped for a symlink after the check fails with `ELOOP`/`ENOTDIR` and is answered 404 — nothing outside the root is read (`share-import` answers the same case with 400 `not_a_file`).
- **`rev`** is `dev:ino:size:mtime_ns` of that fd. The read takes `fstat` before and after; if they differ the bytes are thrown away — retried up to 3 times when the client sent no `expected_rev`, otherwise 409 `changed` with the new rev so the client restarts from the beginning. **What it guarantees:** rev is metadata. Same bytes with a new mtime is a new rev (200, not 304); the client compares content itself. An edit that keeps both size and `mtime_ns` (a tool that restores mtime) is not seen.
- **ETag / 304.** Weak ETag over rev + requested encoding + range (+ response format version and `VT_FS_MAX_BYTES`), `Cache-Control: private, no-cache`. Matching `If-None-Match` → 304, no body. The browser may now keep file contents in its private HTTP cache (always revalidated); the service worker never caches `/api/`. `vtFetch` throws on non-2xx, so the viewer uses `vtFetchConditional`, which treats 304 as success.
- **Range reads** are in bytes and end on a line end, so UTF-8 / CP949 / EUC-KR / Shift_JIS characters are never split (`\n` is never a trail byte in these); UTF-16 looks for the 2-byte `\n` at even positions and refuses odd offsets. A window with no line end is cut at a character boundary (incremental decoder state, not a guess) with `line_truncated`, and `next_offset` continues inside that line. A window too short for one character is a 400 rather than a reply that makes no progress. `tail=N` drops the partial first line (for UTF-8 with no line start in the window it skips continuation bytes; for CP949/Shift_JIS it cannot know the boundary, so the first character may be garbled).
- **Encoding `auto`:** BOM → strict UTF-8 (only when the first 8KB has no NUL — NUL is valid UTF-8) → BOM-less UTF-16 guess (NULs on even or odd bytes only, and the decoded head ≥95% printable, so binaries with NULs in one lane stay binary) → `unknown` (UTF-8 with replacement, `encoding_reason: not_utf8`). Binary is judged after UTF-16, so UTF-16 text is no longer shown as binary. CP949 is never guessed; the user picks it. An explicit choice that hits invalid bytes still decodes (replacement) with `encoding_confident:false`, `encoding_reason: decode_errors`. Auto judges the bytes of each response, so a client reading in ranges should pin the encoding from its first response.
- **Old clients:** without range parameters the reply is the old shape (first 512KB, `truncated`) plus new fields. The viewer itself now always reads in ranges. The host relay already forwards `If-None-Match`, `ETag` and `Cache-Control`, so all of this works on a remote host (decision D7: read features are remote too).
- Tests: `test_fs_read.py` (304, ranges at boundaries, multibyte splits per encoding, unknown → reason, symlink swaps, fs pool), `test_peer_relay.py` (`test_host_relay_fs_file_keeps_etag_304_range_and_409`). Viewer side: `frontend/tests/viewer-file.test.js` (ranges up to 4 MB with the pinned encoding and `expected_rev`, 「더 보기」, 304 → no change, three 409s → 「계속 바뀌는 중」, tail, the encoding select, another host's relay path, `joinPiece`/`eolKinds`), `api-timeout.test.js` (`vtFetchConditional`), `link-scan.test.js` (`splitPathLine`) and the browser smoke `tests/e2e/test_smoke.py` (6 MB file + 「더 보기」, tail gutter, CP949 and mixed line endings, line jump, refresh → 304, a 1.5 MB single line, a terminal `path:line:col` click).

### File storage / upload

`~/.vt/files/` (id-based, 0700 dir/0600 files) — there is no path-based upload directory. Uploaded via keybar paperclip (SVG) slot (mobile — stays visible even when the keybar is collapsed) or `Mod+K` → "파일 업로드"; **pasting an image into the terminal uploads it too**. Size cap `VT_MAX_UPLOAD_MB` (default 2048, i.e. 2GB) enforced streaming → 413; total cap `VT_FILES_MAX_GB` (default 5) and `VT_FILES_TTL_DAYS` (default 30) enforced by a cleanup pass on startup + every 6h — files with an active share or `pin` are excluded from cleanup. **Dropping files from the desktop uploads them too** (desktop drag and drop): onto a terminal pane, they upload and the paths are pasted into that pane's session; onto the files panel (dock or pane), they upload and the list refreshes but nothing is typed — you are filing, not typing. Folders are skipped, several files go one request at a time (the endpoint takes one file), and a drop that lands anywhere else is swallowed with a hint instead of letting the browser navigate away to the file and lose the session. All of it, plus the `#file-input` triggers, runs through `frontend/js/term/upload.js` — the one implementation. The `#file-input` element is shared by all upload triggers (keybar, palette, the panel's 올리기 button) — never add a second one. **API is id-only** (`server/file_store.py`) — `GET /api/files/{id}/download` (`attachment`+`nosniff`+`no-store`), `DELETE /api/files/{id}`, `POST /api/files/{id}/insert` (types the path into a tmux pane, no Enter). There is no path-based download API

**Inserted paths are shell-quoted.** The path typed into a pane (upload with `insertPath`, `POST /api/files/{id}/insert`, `fsh files insert`, the 파일 tree's 「경로 삽입」 (row button, row menu, ⌥Enter) — `viewer/tree.js` `pathInsertText`, where the name comes from whatever is inside the browse root: a cloned repository, an unpacked archive) must not contain the file name as is, because the name is chosen by the sender (a paired Mac's `x-peer-file-name`, a received file): `a$(touch x).png` or a backtick/`;` name would run when the person pressed Enter. `shell_quote_path` (`server/shell_quote.py`, mirrored by `frontend/js/lib/shell-quote.js`) leaves paths made of letters, digits, marks and `_@%+=:,./-` alone — ordinary uploads and Korean names pass through unchanged — and wraps anything else in single quotes (`'` becomes `'"'"'`); a first character of `=`, `%`, `-`, `+`, `~` is quoted too (zsh `=cmd`, job specs, options). The server entry point is `tmux_target.type_path_to_tmux`; plain `type_to_tmux` stays for text that is not a path. The same helper quotes the install directory in the hook commands written to `~/.claude/settings.json` and `~/.codex/config.toml` (`claude_hooks.hook_command`, `codex_hooks.hook_command`): a folder with a space or `$` would otherwise break or be interpreted by the shell. **Paths with control characters are not inserted at all.** Quoting only matters once the shell parses the line; the bytes first pass through the tty line discipline, readline or ZLE, which act on `^U` (kill line), `^W`, `\r` (Enter) and the rest no matter where the quotes are — a name like `x\x15touch /tmp/pwn\r` would erase the opening quote and run `touch` before the person pressed Enter (`send-keys -l` and `sendToPty` write raw bytes; a bracketed paste does not help either when the pane has bracketed paste off). So any path with a C0 control character (0x00–0x1F) or DEL (0x7F) is refused at every insert site with a toast or error saying why: `shell_quote.has_control_chars` / `hasControlChars` (`lib/shell-quote.js`), checked in `tmux_target.type_path_to_tmux` (sends nothing, returns False), `POST /api/files/{id}/insert` (400 `unsafe_path` with a reason), `fsh files insert`, the paired-Mac receive (`POST /api/peer/file` — it also types through `type_path_to_tmux` now, so the sender-chosen name is quoted; before it typed the path as is), the upload insert (`term/upload.js` pastes only the safe paths) and the 파일 tab (`viewer/tree.js` `insertPathToTerminal`). Stored upload names already lose control characters (`file_store._safe_name`), so in practice this bites browse-root names. Tests: `test_shell_quote_path.py` (round-trips through a real `sh`; the refusal is checked at the `subprocess.run` that would call tmux), `test_routes_files.py`, `test_routes_peer.py`, `frontend/tests/shell-quote.test.js`, `frontend/tests/viewer-tree-insert.test.js` and `upload.test.js` (the bytes handed to `sendToPty` / the `paste` WebSocket frame).

### Share links

`POST /api/files/{id}/share` (elevated) issues a `v1.<exp>.<fileId>.<shareId>.<hmac>` token signed with the same key as session cookies (`auth.sign_payload`) — `GET /s/{token}` is the public entry point, deliberately outside `TokenAuthMiddleware`'s usual gate (`server/routes/share.py` does its own verification). **`device` mode**: requires a registered `vt_device` + valid `vt_session`; missing either → 302 to `/?next=/s/{token}` (login gate redirects back after auth, `frontend/js/gate.js`). **`pin` mode**: static PIN page (no app chrome) → correct PIN sets a 60s one-time download cookie; 5 failed attempts cancels the share. **One-time is enforced on the server:** `file_store.claim_download` checks the cookie's hash and deletes it under the store lock in one step, then the file is sent. It used to only verify and ask the browser to drop the cookie, so the same value worked for 60 seconds, from several requests at once or from a copied cookie. The same claim counts the view and removes a `once` share, so a `once` link (either mode) serves exactly one of several concurrent requests. **Resuming (`Range`):** the claim keeps the consumed cookie's hash on the item (`dl_resumes`: shareId, hash, the cookie's original expiry, `once`) and the download response no longer tells the browser to drop the cookie, so a browser or download manager that resumes a broken transfer gets the rest instead of the PIN page. `routes/share.py` `_try_resume` runs before `_resolve` (a `once` share's record is already gone) and accepts a request only when all of these hold: a single `Range: bytes=N-[M]` with an explicit start `N ≥ 1` and below the file size, the same cookie value (`file_store.claim_resume`), before the cookie's **original** expiry (`DL_COOKIE_TTL`, 60 s after the PIN), the share still exists unless it was a consumed `once` share, and an `If-Range` (if sent) matching the file's ETag/Last-Modified — on a mismatch Starlette's `FileResponse` would drop the range and send the whole file. A resume does not count a view. Everything else falls through to the normal path: a plain re-GET, `bytes=0-`, a suffix range (`bytes=-N`) or several ranges get the PIN page (or 404 for a consumed `once` share), so no new whole download starts without the PIN, and a `once` link never sends the file from byte 0 twice. Trade-off: until that expiry a holder of the cookie value can still fetch bytes 1..end by range — the same 60-second window as before the one-time fix, but only for ranges that skip byte 0. A transfer still running past the 60 s cannot be resumed; the visitor enters the PIN again. Expired `dl_resumes` entries are dropped on the next claim for that file and by the cleanup pass. **The limit is atomic:** `file_store.reserve_pin_attempt` reads the share and bumps `attempts` under the store lock *before* the PIN is checked. Judging from a snapshot taken at the start of the request would let parallel requests all see `attempts=0` and all be verified, defeating the limit. Each wrong guess also counts toward the pre-auth source lockout (`share_pin`), the form body is read through a 4KB cap (413 above it; buffering the whole body on a pre-login route is not acceptable), and **new** PINs must be 6–20 characters (`MIN_PIN_LEN`; `fsh files --pin` generates 6 hex characters). Tests: `test_share.py` (including concurrent and replayed cookies, concurrent `once` downloads, `Range` resume within and after the window, refused plain/whole-file re-requests, `once` resume), `test_file_store.py` (`claim_resume`). Store calls on these routes and on `/api/upload` run in a thread (`asyncio.to_thread`) — the store's flock waits up to 5 s while the CLI holds it, which on the event loop froze the whole server; `test_no_blocking_in_async.py` lists the `file_store` calls. Cancelling (`DELETE .../share/{shareId}`) removes the record from `files.json` — the URL 404s immediately even though the signature is still cryptographically valid. `once` shares self-delete after the first successful download. The Files panel provides share issuance and revocation controls

### Sharing from the 파일 tab (snapshot import)

Share links only attach to file-store (id) files (the path-based `/api/fs/download` above is for the browser itself, not for links). So the 파일 tab row button, the viewer header button (sheet/float) and the pane viewer's floating button call `POST /api/fs/share-import {path}` (`routes/share.py`, elevated): `fsguard.resolve_under_roots` (root, denylist, hidden dirs), then the file is opened with `fsguard.open_resolved`: the resolved path is walked from `/` one component at a time with `O_DIRECTORY|O_NOFOLLOW` relative to the previous directory fd, the last component with `O_NOFOLLOW|O_NONBLOCK`, and checked regular via `fstat`. A symlink swapped in after `resolve()` — for the file **or any parent directory** — fails with `ELOOP`/`ENOTDIR` (400 `not_a_file`); plain `O_NOFOLLOW` only covers the last component, so a parent swapped for a link to outside the root used to copy that outside file. Symlinks that were inside the root at check time still work, because `resolve()` already expanded them. The file is then size-capped by `VT_MAX_UPLOAD_MB` while streaming, and copied into the store with `origin=fs:<path>:<size>:<mtime_ns>`. The same unchanged source reuses its snapshot; a changed source makes a new one. The snapshot does not follow later edits to the original, and the dialog says so. Then `openShareDialog` (same dialog as the 첨부 tab) issues the link; elevation is asked once and retried.
