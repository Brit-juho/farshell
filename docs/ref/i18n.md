# Display language (ko / en)

FarShell ships in Korean and English. One value per server picks the language for the
web app, the server messages and the `fsh` CLI.

## Where the language comes from

`server/i18n.py` (`current()`) resolves it in this order:

1. `VT_LANG` in `~/.vt.env` (`ko` or `en`). The file wins over the environment so that a
   stale `VT_LANG` export in a shell or tmux server can't override what the settings screen
   just saved.
2. `VT_LANG` in the process environment.
3. OS locale: `LC_ALL`, then `LC_MESSAGES`, then `LANG` (`C`/`POSIX` are skipped). `ko*` → Korean,
   anything else → English.
4. English.

`install.sh --lang ko|en` writes the value at install time (an agent running the install passes
the language the user is speaking). Without the flag the installer keeps an existing value,
otherwise asks (terminal) or follows the OS locale.

The settings screen (Appearance → Language) calls `PUT /api/lang`, which writes `VT_LANG`
through `lib/vt_env.sh`, then reloads the page. Endpoints: [`API.md`](../../API.md).

## How the web app gets it

The server serves `/` itself (not as a static file). `i18n.render_index()`:

- sets `<html lang>`;
- replaces the `<!--vt:i18n-->` marker with `<script src="/static/js/locales/en.js?v=…">` when
  the language is not Korean;
- translates the link-preview `<meta>` tags, because crawlers don't run JavaScript.

So the language is known before any script runs. Nothing is fetched asynchronously, and the
first paint is never in the wrong language.

## Translating strings

Keys are the **Korean source text** (gettext style):

```js
import { t } from '../core/i18n.js';
el.textContent = t('세션 닫기');
toast(t('남은 시도 {n}회', { n }));
```

- Korean needs no dictionary. A string missing from `en.js` falls back to Korean.
- `frontend/js/locales/en.js` holds `{ "한국어 원문": "English" }`. The body must be JSON.
- Plurals: `{ "one": "1 attempt left", "other": "{n} attempts left" }`, chosen by `vars.n`.
- Placeholders are `{name}` and must match between source and translation.
- Static HTML: add `data-i18n` to an element to translate its text (direct text nodes when it
  also holds an icon), and `data-i18n-attr="placeholder,aria-label"` for attributes.
- The classic script `js/i18n-boot.js` is the implementation (`window.vtT`), because the login
  gate runs before ES modules. `core/i18n.js` wraps it and returns the source text when the
  global is missing (node tests).

## Server messages

Python code calls `tr('한국어 원문', n=…)` (`server/i18n.py`). It reads the same `en.js`; the language is one
value per server, so a response never depends on the request. Rules that keep it correct:

- Call `tr()` at use time. At module level it freezes the language the server started with, so a
  constant that holds text becomes a function.
- Never translate what an agent or tmux receives, what gets stored in a file, what another piece
  of code compares against, or log lines.
- When the frontend compares a server string, both sides wrap the same Korean key (the dictionary
  makes them the same English).

## CLI (bash)

`lib/i18n.sh` resolves the language in the same order and provides `_t '한국어 원문' name=value …`.
bash 3.2 (macOS) has no associative arrays, so the dictionary is a generated `case` function:
`lib/locales/en.sh`, built from `en.js` by `python3 scripts/gen_cli_i18n.py` (CI fails if it is stale).

- Keys are single-quoted literals on one line; values go in `{name}` placeholders. Emoji and indent stay
  outside the key. Shell has no plural forms, so write "{n} session(s)".
- Multi-line text (heredocs, boxes) is split with `vt_is_en`, and the English body sits next to the Korean one.
- `fsh help <topic>` reads `docs/help/en/<topic>.md` in English and falls back to `docs/help/<topic>.md`.
  Every topic needs both files.

`python3 scripts/check_i18n.py --strict` (CI) fails on missing keys, unused keys and placeholder
mismatches. `--untagged` lists Hangul literals not yet wrapped in `t()`.

When you change Korean copy, change the key in `en.js` in the same commit.

## Translation style

Translate for meaning, not word for word. Write the way English developer tools talk: short,
direct, sentence case, no trailing period on labels and buttons, "Couldn't …" rather than
"Failed to …" in user-facing errors.

## Writing UI names in documents

Public documents (`docs/ref/`, `docs/help/en/`, `DESIGN.md`, `CLI.md`, `API.md`, `README.md`,
`ARCHITECTURE.md`, and `CHANGELOG.md` from 2.7.0 on) are written in English. An English reader sees
the English UI, so a screen label is cited by the name that appears there:

- **Form: `English name (한국어 이름)`**, for example `Settings → Appearance (모양)`. The English name
  comes from `frontend/js/locales/en.js` (the value of the Korean key) and, for a term, from the glossary
  below, which wins when the two differ. Give the Korean name in parentheses once per paragraph or
  list item (the first mention); later mentions in the same paragraph use the English name alone.
- **A name that isn't in the dictionary** keeps the Korean only, quoted with 「…」, until it gets an entry in
  `en.js`. Don't invent an English name in a document.
- **Korean literals stay as they are** when the exact Korean text matters: strings matched in code or terminal output,
  regular expressions, keys of `en.js`, and examples of what the Korean UI prints. Put them in backticks or 「…」.
- **`docs/help/en/` is stricter:** it has no Korean at all outside fenced code blocks
  (`server/tests/test_cli_i18n.py` enforces it), because `fsh help` prints it in a terminal for an English
  reader. Cite only the English name there, and put a Korean literal the reader must type or match in a code block.
- **Don't translate the heading anchor away**: headings use plain English, and a link to a heading follows the
  English slug (`[File tree](#file-tree-files-activity-vt-dir)`).
- **The check:** `scripts/check_docs.py` counts lines in `docs/ref/` and `docs/help/en/` that have Korean outside
  backticks, 「…」, quotes and `( … )` glosses, and prints a note (not a failure) when the count is above its limit.
  This file is skipped because the glossary and the Korean copy rules below are Korean by nature.

## Korean copy rules

The Korean text is the key, so these rules apply to the source strings themselves.

**English terms.** Write the Korean word and put the English term in parentheses only the **first
time it appears on a screen** (「폴더 점유(lease)」), then Korean only. Command names, flags, file
names, protocol names and product names (`fsh`, `tmux`, MCP, OSC52) stay as they are. Search keyword
lists (`panels/settings/index-data.js`) may keep English synonyms because people type them.

**Internal numbers.** Never show ADR, plan or section numbers (「ADR-27」, 「N36 §5」) to the user.
Keep them in code comments.

**Buttons.**

| Word | Use it for |
|---|---|
| 저장 | writing a value (edits, names, categories) |
| 적용 | changes that take effect immediately (a setting, a reviewed plan) |
| 확인 | acknowledging information, or verifying a password |
| 닫기 | closing a window or panel |
| 취소 | stopping an action in progress; the cancel button of every confirm dialog |
| 나중에 | postponing a decision (approval requests) |

A confirm dialog for a risky or irreversible action has a title and a confirm button that **name the
action** (「삭제」「종료」「연결 해제」「회수」「공개」), never a bare 「확인」. Every `confirmDialog`
call passes `title` and `okLabel`; `promptDialog` passes them when the value is saved or created.

**Removing things.** 삭제 = the data is gone (files, records, models). 제거 = taken out of a list or
setup while the original stays (plugins, API settings). 해제 = turn off a state or link (선택 해제,
공유 해제, 터널 해제, 점유 해제). 회수 = take back a permission that was granted. 비우기/지우기 = empty
an input or a cache. Don't mix them for the same action (not 「지웠습니다」 next to 「삭제하지 못했습니다」).

**Tone.** Sentences end in 「~합니다/~하세요/~할까요」 (814 of the 1,159 sentence-like strings before this
cleanup; noun forms 343, plain 「~다」 2, 「~해요」 0). Short labels, chips and hints may be noun forms
(「저장됨」「삭제 실패」). Questions in dialogs end in 「~할까요?」, not 「~하시겠습니까?」.

**Periods.** Body text that stays on the screen (descriptions, help lines, empty states, dialog
bodies) ends with a period. Toasts, tooltips, button and chip labels and one-line status values do not.
Inside one string, sentences are separated by a period and the last one follows the same rule.

**Length.** Cut repeated or obvious words, never the warning, the reason or the way back.

## Checklist for a new feature

A feature is finished only when both languages are. Before committing:

1. Every new user-visible string is wrapped (`t()` in the frontend, `tr()` in the server, `_t` in
   shell) and has its English entry in `frontend/js/locales/en.js`; placeholders match.
2. If shell strings changed, regenerate the shell dictionary: `python3 scripts/gen_cli_i18n.py`.
3. If the feature changes what a user reads in `README`, `CLI`, `docs/guide` or `docs/help`, update
   **both** language files of the pair in the same commit. `check_docs.py` enforces the
   `docs/help` / `docs/help/en` pairing only; check the others by hand.
4. `python3 scripts/check_i18n.py --strict` passes.
5. Look at the changed screen or command output with `VT_LANG=en` as well as `VT_LANG=ko`.
